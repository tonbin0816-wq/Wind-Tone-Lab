## 0. いま何が在って、何が無いか（2026-09-10 に実装を読んで確認）

App Store ガイドライン 1.2 が UGC アプリに求める4点と、現状の照合。
**「ひとつも満たしていない」と一度報告したが、それは確認せずに言った誤りだった。** 正しくは下表。

| 1.2 の要求 | 実装 | 場所 |
|---|---|---|
| ① 不適切な内容のフィルタ | **在る（クライアント側のみ）** | `src/community/profile.js:124` が `ngwords/filter.js` の `findNgWord` を呼び、NG なら「このニックネームは使用できません」で保存前に止める。辞書は日本語 320 語（`generated/ja.json`）+ 英語（上流 dsojevic/profanity-list）。NFKC・カナ統一・leet 変換のうえ、強い語は部分一致・穏当な語は語境界一致という2段構え |
| ② 通報の仕組み + 迅速な対応 | **無い** | `src/` に通報の UI も `reports` 集合も無い。`firestore.rules` は `users` と `ideals` 以外を全拒否。設計書 §8.1 に「通報ボタン — 理由は選択式」「通報1件で即・自動非公開」と**書いてあるだけ** |
| ③ ユーザーをブロックする機能 | **無い** | 同上 |
| ④ 連絡先の公開 | **無い** | `src/` に `mailto:` / 問い合わせ / 連絡先 の綴りが無い |

あわせて確認したもの:

- **5.1.1(v) アカウント削除** — **在る**（`CommunityTab.jsx:1104`「アカウントを削除」。`idealRepo.unpublishAllIdeals` が目安も取り下げる）
- **§7.4 の文書（プライバシーポリシー・利用規約）** — **無い**（リポジトリに文書も、それへのリンクも無い）
- **サーバ側の検査** — `firestore.rules` だけ。**Cloud Functions は使わない**（`2026-09-02` 設計書の決定1: Blaze プラン＝カード登録が要るため）。①のフィルタは**ルールでは再現できない**ので、生 SDK を叩く相手はフィルタを素通りできる。②の通報がその受け皿になる

### ①のフィルタは「サーバ側でも」検証する設計だったが、していない

§8.1 は「検証の本体はサーバ」と書いているが、Cloud Functions を使わない決定1と両立しない。
ルールで数百語の部分一致は現実的に書けない。**この計画では①を「クライアントで止める + すり抜けは②で受ける」と再定義する。** 審査ノートにもそう書く。

## 1. 本人の問いへの答え

**「ブロックは必要か。メッセージが来るわけでもなく、任意入力はニックネームだけなのに」**
実質の指摘はそのとおりで、Ficus でユーザー間に起きる接触は「相手のニックネームと数値が自分の画面に出る」だけ。
だから Ficus でのブロックとは**「その人を自分の画面から消す」以上のことは物理的に無い**。
一方、Apple の要求文は "The ability to block abusive users from the service" と一般形で書かれていて、
調査レポート（2026-08-27）は「ニックネームだけなら免除」という規定を**探して見つけられなかった**。
結論: **作る。ただし最小形（自分の一覧から隠す。設計書 §8.1 の定義そのまま）でよく、サーバは要らない。**

**「連絡先はだれの連絡先か」**
**運営者＝本人の連絡先**。原文は "Published contact information so users can easily reach *you*"（you = 開発者）。
個人のアドレスである必要は無く、専用のメールアドレスで足りる。App Store 提出時の「サポート URL」にも同じものを使う。

## 2. 作るもの（凍結）

### 2.1 通報 → 自動非公開（Cloud Functions 無しで成立させる形）

**制約**: 通報者は他人の `users/{uid}` を書けない（ルール: 本人のみ）。だから「通報したら相手の `isPublic` を落とす」は**書けない**。
**採る形**: **読む側が隠す。** 通報は別の集合に置き、一覧を読む側がそれを見て当該 uid を落とす。

| 集合 | 誰が書く | 誰が読む | 中身 |
|---|---|---|---|
| `flags/{targetUid}` | 通報者（本人以外。認証済み） | **誰でも**（一覧を読む側が隠すため） | `{ createdAt }` だけ。**通報者は入れない**（誰が通報したかを全員に晒さない） |
| `reports/{targetUid}_{reporterUid}` | 通報者（create のみ） | **クライアントからは読めない**（`allow read: if false`）。運営者は Firebase コンソールで読む | `{ targetUid, reporterUid, reason, createdAt, status: "open" }` — 監査と「通報者を数える」（§8.1 追記の3）のため |
| `banned/{uid}` | **クライアントからは書けない**。運営者がコンソールで置く | ルールが `exists()` で参照するだけ | `{ createdAt, note }` |

- 一覧（データ / 順位 / シェア）は `users` を読んだ後、`flags` を `limit(50)` で読んで**当該 uid を落とす**。目安（`ideals`）も `ownerUid` が flags に在れば落とす。読む側で隠すので**通報から反映までは即時**（"timely" は満たす）
- **本人に知らせる**（§8.1 追記の1）: 自分の `flags/{myUid}` が在ればマイページの先頭に「通報により一時的に非公開になっています。運営が確認後、問題なければ公開に戻ります。急ぐ場合は下の連絡先へ」を出す。黙って消さない
- **戻す**（同2）: 運営者がコンソールで `flags/{uid}` を消す。**管理画面は作らない**（運営者の uid が匿名認証で端末に縛られるので、ルールで運営者を名指しできない。コンソールはルールを通らないので、これで足りる）
- **BAN**（§8.1）: 運営者が `banned/{uid}` を置く。`users` / `ideals` / `flags` / `reports` の create・update に `&& !exists(/databases/$(database)/documents/banned/$(request.auth.uid))` を足す。BAN された端末は書けなくなり、既存の公開分は運営者がコンソールで `isPublic` を落とす
- **通報の入口**: 人物紹介（`PersonSheet`）の末尾に「この人を通報」。押すと `BottomSheet`（器は1つ、§4.5）で**理由を選択式**で出す。自由記述は置かない（自由入力を増やさない §8.1）
- **理由の列挙**（ルールと `profile.js` の写しで固定。列挙の同期は `profile.test.js` の既存の作法に足す）: `不適切なニックネーム` / `なりすまし` / `その他`
- 二重通報: docId が `target_reporter` なので同じ人からは1件しか作れない（上書きは update を拒むので不可）
- 自分自身は通報できない（ルール: `targetUid != request.auth.uid`）

**受け入れる弱点**（設計書 §8.1 追記が既に認めているもの）: 通報1件で他人を隠せる。対策は「本人に知らせる + 運営が戻す + 通報者を数える」の3つで、上の形はその3つを全部持つ。

### 2.2 ブロック（自分の一覧から隠す）

- **端末内だけ**（IndexedDB の `kv` に `blockedUids: string[]`）。サーバに何も書かない
- 人物紹介の末尾に「この人を非表示にする」。押すとその場で閉じ、以後 データ / 順位 / シェア / 目安 の集計から落とす（`aggregate.js` の入口で `users` を絞る。**数える前に落とす**ので母数からも消える）
- 解除: マイページに「非表示にした人」の一覧（ニックネームと解除ボタン）。0人なら行ごと出さない
- 機種変更で消える。プロフィールと同じ扱い（匿名アカウントも端末に縛られている。§1 JoinIntro の文言と揃う）

### 2.3 連絡先の公開

- マイページの末尾（「アカウントを削除」の**上**。破壊的な一手が最後、という並びを崩さない）に「お問い合わせ」行。押すと `mailto:` で開く
- 参加前の画面（`JoinIntro`）の説明文の末尾にも同じアドレスを1行
- **アドレスは本人が決める**（§4 の決定事項）。専用アドレスを推奨

### 2.4 プライバシーポリシー・利用規約（§7.4）

- 静的ページを2枚、Vite の `public/` に置いて本番 URL で配信（`/privacy.html` `/terms.html`）。App Store の「プライバシーポリシー URL」「サポート URL」にそのまま使える
- マイページの「お問い合わせ」の隣に「プライバシーポリシー」「利用規約」のリンク。参加前の画面にも
- 中身の骨子は §7.4 のとおり: 収集項目（匿名 uid・ニックネーム・楽器の組・練習日数・目安の数値）/ 利用目的 / 第三者提供なし / 削除の窓口（アプリ内の「アカウントを削除」+ 連絡先）/ 13歳以上 / 第三者の演奏を上げない / 練習量の値は検証していない
- **文面の最終確認は本人**。私は法律の専門家ではないので、骨子と下書きまで

### 2.5 審査ノート（提出時に書く文）の材料

- ①はクライアントで止める設計。すり抜けは②で受ける
- ②は通報から非公開まで人手なし・即時。本人への通知と運営の復旧手順あり
- ③はユーザー単位で隠せる
- ④はアプリ内と URL の両方
- 5.1.1 は実装済み

## 5. 手順とゲート

**順序は必ず「ルールを公開 → アプリを配信」**（逆にすると新しい集合へ書くクライアントが旧ルールに弾かれる。`ficus-open-threads` の教訓）。

1. `firestore.rules` に `flags` / `reports` / `banned` を足し、`banned` の存在ガードを既存の create/update に足す → **本人がコンソールで公開**
2. `src/community/`: 通報のシート・`flags` の書き込み・読む側の隠し・マイページの通知バナー
3. ブロック（端末内）と解除の一覧
4. 連絡先・文書2枚・リンク
5. 検査: `aggregate.test.js` に「flags / blocked の uid は数える前に落ちる」、`profile.test.js` の列挙同期に理由の列挙を足す、`pitch-test` に「通報のシートは BottomSheet」「連絡先はアカウント削除より上」の錨
6. **私はコミュニティの「参加してプロフィールを作る」を押さない**（本番 Firestore に実アカウントが作られる）。通報の疎通は本人の端末で確かめる

合格ライン: `vitest` 全件 / `pitch-test` FAIL 0 / `vite build` 成功 / 本人の端末で 通報→一覧から消える→マイページに通知が出る→コンソールで flags を消す→戻る、の一巡。
