# コミュニティ機能 設計書

作成日: 2026-08-27
対象: Ficus に4つ目のタブ「コミュニティ」を追加し、他の奏者の目安・機材・練習量を共有できるようにする

---

## 1. 背景と目的

現在の Ficus は完全にローカル完結のアプリで、比較対象は「過去の自分」か「目の前でこのアプリに向かって吹いてくれた人」しかいない。

この機能の**核は「目安プロファイルの共有」**である。既存の目安(理想値プロファイル)は、音声を含まない小さな数値データとしてすでにアプリ内に存在する。これを共有可能にすれば、「このアプリを使っている誰の音でも目安にできる」状態が作れる。

達成したいことは3つ:

1. **他の奏者の指標を自分の目安として取り込める** ← 主目的
2. **みんながどんな楽器・マウスピース・リードを使っているか分かる**
3. **練習量のランキングで競争を促す**

---

## 2. スコープ

### やること

- 4つ目のタブ「コミュニティ」の追加
- アカウント登録(Google / Apple サインイン)とユーザープロフィール
- 目安プロファイルの公開・検索・取り込み
- コホート平均目安の自動生成
- 練習量ランキング / 目安採用数ランキング
- 楽器・マウスピース・リードのシェア表示
- プライバシーポリシー・利用規約・通報/ブロック・アカウント削除

### やらないこと(明示的に対象外)

- **録音音声の共有** — ストレージコスト、著作権、第三者の音声を上げる問題がすべて一度に発生する。数値のみ共有する
- **セッション単位の生データの共有** — 共有するのは目安プロファイル(音ごとの平均値)と集計値のみ
- **音量(dB)の共有** — マイク距離・入力ゲイン・AGC に完全に支配され、他人の値に意味がない
- **全データのクラウド同期** — クラウドは公開用の写しであり、ローカル(IndexedDB)が常に正
- **収益化** — 別案件

---

## 3. 目安の共有方式(本設計の中核)

### 3.1 問題

計測値は録音環境で大きく変わる。他人の絶対値をそのまま目安にすると、全音で一律に「足りない」と表示され続け、どの音を直せばよいのか分からない。指標ごとに環境依存度はまったく異なる。

| 指標 | 環境依存の要因 | 依存度 |
|---|---|---|
| ピッチ | (ほぼ無し) | 極小 |
| 倍音構成(比率) | マイクの周波数特性 | 中 |
| スペクトル重心 | マイクの周波数特性、部屋の反響 | 中〜大 |
| HNR | 暗騒音 | 大 |
| 音量 dB | マイク距離、入力ゲイン、AGC | 極大 |

### 3.2 解決策: 平行移動して形を比べる

**他人の折れ線を、自分の位置まで平行移動してから形を比べる。** 音名ごとの比較はそのまま残り、線の本数も減らない。線を横に滑らせるだけ。

指標ごとの扱い:

| 指標 | 共有方法 |
|---|---|
| ピッチ | そのまま共有。基準ピッチ(440/442)の差はプロファイルの `tuningHz` で換算する |
| 倍音構成 | そのまま共有。音の中での比率なので距離・ゲインでは動かない |
| スペクトル重心 | **平行移動して共有** |
| HNR | **平行移動して共有** |
| 音量 dB | **共有しない** |

### 3.3 平行移動の基準

**自分と相手の両方が持っている音名だけを取り出し、その中央値を合わせる。**

```
オフセット = median(自分の値, 共通音名) - median(相手の値, 共通音名)
取り込む値[音名] = 相手の値[音名] + オフセット
```

- **共通音名で基準を作る理由**: 相手が2オクターブ、自分が5音しか録っていない場合、互いの全音平均は数えている音が違うため比較できない
- **平均ではなく中央値を使う理由**: アルティッシモの裏返りなど1音の外れ値で線全体がずれるのを防ぐ
- **共通音名が3音未満の相手は一覧に出さない**: 基準が立たないため

### 3.4 取り込む側にデータが無い場合

自分の中央値が無ければ平行移動できない。この場合は相手の絶対値をそのまま入れ、**「参考値」であることを画面に明示する**。自分の計測が溜まった後に取り込み直すよう促す。

### 3.5 環境差の残余リスクへの補助

平行移動でも消えないのは、マイクの周波数特性の差(倍音構成・重心に効く)と、部屋の反響の差である。以下で緩和する:

- **端末クラスでの絞り込み** — iPhone / Android / PC を自動判定して保存する。機種名までは取らない。同じ端末クラス同士なら周波数特性が近い
- **練習場所タグ** — 絞り込みと解釈の補助として使う(後述)

## 4. データモデル

### 4.1 ユーザープロフィール

楽器・マウスピース・立場は頻繁に変わらないので**セッションではなくユーザーに紐づける**。リードは既存どおりセッションに紐づく。

**自由入力は「ニックネーム」1つだけ。他はすべてプルダウンから選ぶ。** これはモデレーション負荷を構造的に消すための設計判断である。

| 項目 | 形式 | 備考 |
|---|---|---|
| ニックネーム | 自由入力 | 唯一の自由入力。「公開されます」の注意書きを添える |
| 楽器種別 | 選択 | 既存 `saxType` と同じ値。目安の互換性判定に使う |
| 楽器ブランド | 検索選択 | YAMAHA / SELMER / YANAGISAWA / ... |
| 楽器モデル | 検索選択 | ワードを入力すると部分一致で候補が出て、そこから選ぶ(自由確定は不可)。カタログはクラシックからジャズまで網羅する |
| マウスピースブランド | 検索選択 | 同上 |
| マウスピースモデル | 検索選択 | 同上 |
| マウスピース開き | 選択 | モデルに応じた候補 |

楽器・マウスピースのカタログはアプリ側が持つデータであり、ユーザーが文字列を確定させることはない(部分一致はあくまで**候補を探すための入力**で、公開されるのは選んだカタログ項目のみ)。したがってモデレーション対象は増えない。カタログに無いモデルは「その他(ブランドのみ)」を選んだうえで、連絡先メール宛に追加リクエストできる案内を置く。
| 立場 | 選択(単一) | 中学吹奏楽部 / 高校吹奏楽部 / 大学吹奏楽・サークル / 音大生 / 社会人 / 講師・プロ / 独学 |
| 演奏開始年 | 選択(西暦) | **「楽器歴◯年」ではなく開始年で持つ**。年数で持つと翌年には嘘になる。表示時に計算する |
| ジャンル | 選択(複数) | クラシック / ジャズ / ポップス / その他 |
| 編成 | 選択(複数) | ソロ / アンサンブル / ビッグバンド / 吹奏楽 / オーケストラ |
| 練習場所 | 選択(複数) | 自宅 / 学校の音楽室 / 個人練習室 / スタジオ / カラオケ / 屋外 |
| 端末クラス | 自動判定 | iPhone / Android / PC |
| 公開設定 | 公開(既定) / 非公開 | |

**収集しないもの**: 本名、生年月日、学校名、メールアドレス以外の連絡先。登録時に「13歳以上です」のチェックのみ取る(理由は §7)。

### 4.2 公開目安プロファイル

既存の理想値プロファイル(`notes{semitoneIndex: {...}}` + `saxType` + `tuningHz`)をそのまま持ち上げ、以下を添える。

| 項目 | 備考 |
|---|---|
| 作成者プロフィールへの参照 | スナップショットではなく参照。属性が変わったら追随する |
| リード情報 | 由来セッションで使われていた銘柄・硬さ・**使用日数**。開封日そのものは共有しない |
| 元セッション数 | 信頼度の目安として表示 |
| 採用数 | 何人がこれを目安に取り込んでいるか(●票) |
| 収録音名の一覧 | 共通音名の判定に使う |

**プロファイルの構造は変更しない。** 取り込んだ他人の目安は既存の目安リストにそのまま並び、計測タブは他人由来かどうかを知らないまま動く。

### 4.3 コホート平均目安

「音大生・クラシック・アルト」のような条件に合う公開プロファイルを平均して自動生成する。既存の `buildIdealProfileFromSessions()` は複数セッションを平均する関数なので、**平均する対象がユーザーをまたぐだけで構造は同一**である。

- 平均する前に、各プロファイルを §3.3 の方法でコホート内の基準に平行移動する
- **最低5人以上でないと生成しない**(人数が少ないと個人が特定できてしまう)
- 一覧の先頭に置く。これは「ランダムの誰か1人を選ぶ」ことへの抵抗を消すと同時に、採用数ランキングによる人気の固定化を緩和する

### 4.4 練習量の集計

| 項目 | 定義 |
|---|---|
| 練習時間 | **計測タブ滞在中に、計測下限dBを超え、かつピッチが検出できているフレームの累積時間**。録音していなくても数える |
| 練習日数 | その日の練習時間が5分以上あった日 |

この定義により、チューナーとして使っている時間もメトロノームで練習している時間も自然に含まれる(計測タブ滞在中はマイクとライブ解析がすでに動いている)。同時に、テレビの音や話し声はピッチが安定しないため弾かれ、アプリを開いて放置しても1秒も増えない。

## 5. 画面構成

4つ目のタブ「コミュニティ」を追加し、その中に子タブを4つ置く(既存のリードタブが子タブを持つのと同じ文法に従う)。

### ① 目安をさがす(メイン)

- 絞り込み: 楽器種別(自分と同じで固定) / 立場 / 楽器歴の帯 / ジャンル / 編成 / 練習場所 / 端末クラス
- 結果一覧: 先頭に**コホート平均**、その下に個人プロファイルを採用数順
- カードに表示するもの: ニックネーム、属性タグ、楽器・マウスピース、リード(銘柄・硬さ・使用日数)、元セッション数、採用数
- タップで詳細 → **音名ごとの折れ線で自分と重ねて表示**(縦軸=音名、横軸=値) → 取り込み

### ② ランキング

- 練習量: **練習日数**(主) / **練習時間**(副)。期間は週・月
- 目安採用数: 「あなたの目安が◯人に採用されています」の多い順
- **上位20位まで表示**

### ③ みんなの機材

- リードシェア・楽器シェアを円グラフ
- 楽器 × マウスピース × リードの組み合わせを採用数順のリスト(●票)

### ④ マイプロフィール

- プロフィール編集 / 公開・非公開の切り替え
- 公開する目安プロファイルの選択
- **アカウント削除**(App Store 必須要件)

## 6. アカウントと認証

- **Google サインイン**と**Sign in with Apple**の2つ。Google を提供する以上、Apple は App Store のガイドライン4.8で必須になる
- メールアドレスは認証プロバイダから受け取るが、公開しない
- Apple の「メールを非公開」に対応する

## 7. プライバシー・法務

### 7.1 未成年への配慮

対象はリード楽器奏者の全員であり、学生向けのアプリではない。ただし部活動の文化により利用者に学生が一定数含まれることは避けられず、一般公開のランキングに未成年が並び得る。そのための備えとして以下を設計に織り込む(UI や文言で学生を前面に出すことはしない)。

- **13歳未満は利用不可**。規約に明示し、登録時にチェックを取る
- **学校名の入力欄を作らない**。立場は「高校吹奏楽部」までで止める。これにより個人の所在が絞られない
- 本名を使わないよう、ニックネーム欄に注意書きを添える
- 生年月日は収集しない。年齢確認はチェックボックスのみで足りる

### 7.2 収集する個人情報を最小化する

本名を集めると、個人情報保護法上の「保有個人データ」として開示・訂正・削除請求への対応義務が発生する。今回は決済・契約・配送・本人特定のいずれも無いため、**ニックネームのみで足りる**。

### 7.3 第三者の演奏を勝手に公開させない

既存のセッションには `performer` フィールドがあり、他人の演奏を記録できる。

- **公開できるのは `performer` が「自分」のセッション由来の目安のみ**
- UI で選ばせず、アップロード時のバリデーションでも弾く(二重に防ぐ)

### 7.4 用意する文書

- プライバシーポリシー(収集項目、利用目的、第三者提供の有無、削除請求の窓口)
- 利用規約(13歳以上、第三者の演奏を上げない、練習量の値は検証していない旨)

## 8. App Store 審査要件

後から足すと最も高くつくため、最初から入れる。

| ガイドライン | 要件 | 対応 |
|---|---|---|
| 5.1.1(v) | アプリ内からアカウントを完全削除できること。**匿名(ゲスト)アカウントにも適用され、一時無効化では不十分**(公式FAQで明記) | マイプロフィールに削除導線を置く |
| 4.8 | 第三者ソーシャルログインを出すなら Sign in with Apple も必須。**匿名認証のみなら発動しない**(将来 Google ログインを足した時点で必須化) | 認証方式の決定(§6)に従う |
| 1.2 / 5.1.2 | UGC がある場合、①不適切コンテンツのフィルタ ②通報 ③ユーザー間ブロック ④連絡先の公開、の4点セット+迅速な対応。リジェクト文面の実例は「コンテンツ削除に加えて**ユーザーの排除**」まで要求 | 下記 §8.1 |
| — | プライバシーポリシーURL、App Privacy の申告 | §7.4 |
| — | 2026年9月以降「social media capability」の申告設問が必須。コミュニティ機能が該当し得る | 提出時に回答。詳細は調査レポート参照 |

> 一次ソースの引用と適用解釈は `docs/superpowers/research/2026-08-27-appstore-guidelines.md` にまとめてある。

### 8.1 モデレーションを人力ゼロで回す

自由入力をニックネーム1つに絞ったため、**通報の対象はニックネームだけ**になる。これにより対応を機械化できる。

- **NGワードフィルタ** — 登録時にその場で弾く。公開前に止まるので表に出ない。日本語は MosasoM/inappropriate-words-ja(MIT)、英語は dsojevic/profanity-list(MIT)を採用し、サーバ側で正規化(NFKC・小文字化・カナ統一・leet変換)→部分一致+許可リスト照合。クライアント側は同じ判定をUX目的で併用する(検証の本体はサーバ)。リストは2021年以降更新が止まっているため新語は自前で追加運用する。詳細は `docs/superpowers/research/2026-08-27-ngword-filter.md`
- **通報ボタン** — 理由は選択式
- **通報が1件でも入ったら、そのプロフィールを即座に自動で非公開にする** ← ここが要点
- **ブロック** — その人を自分の一覧から隠す
- **連絡先メールアドレスを公開**
- **アカウントBAN** — 悪質なリピーター(非公開解除後に再度NGなニックネームを付ける等)を運営者がBANできる管理操作を持つ。リジェクト文面の実例が「コンテンツ削除+ユーザーの排除」まで要求しているため

通報から非公開までを自動にすることで、**「迅速に対処する」を人間の在席なしで満たす**。共有されるのは数値だけなので、誤通報で一時的に隠れても被害は小さい(本人の目安が数日見えなくなるだけ)。運営者は後からまとめて確認して戻せばよい。

> **裏取り済み(2026-08-27)**: 「24時間以内」はガイドライン本文に無く、本文の要求は "timely responses"。ただし自動非公開単体では 1.2 を満たさず、フィルタ・通報・ブロック・連絡先公開の4点セット+BAN手段が必要。原文引用は調査レポート参照。

## 9. バックエンド構成とコスト

**Firebase を採用する。** Sign in with Apple / Google の実績が最も厚く、Capacitor でのネイティブ化との組み合わせ事例も豊富で、今回の最難関である「認証 + アカウント削除 + 審査」を最も枯れた道で通れる。

### 9.1 構成

| 用途 | サービス |
|---|---|
| 認証 | Firebase Authentication |
| データ | Cloud Firestore |
| 集計バッチ | Cloud Functions(日次) |

### 9.2 Blaze プランが避けられない理由

ランキング・円グラフ・コホート平均を**都度クエリで作ることはできない**。1000人規模で全員の値を読むと、1回のランキング表示で1000 read が発生し、全員が1日1回開くだけで100万 read/日となり、無料枠(5万 read/日)を初日に超える。

したがって**事前集計が必須**であり、そのためには Cloud Functions が必要で、Cloud Functions は Blaze プラン(従量課金)でしか使えない。

対応:

- **Blaze プランに上げる。クレジットカード登録は避けられない**
- 予算アラートを設定する
- Cloud Functions の同時実行数に上限を設定する
- 実際の使用量は無料枠に収まるため、請求は実質 0 円になる見込み

### 9.3 同期の方針

**クラウドは公開用の写しであり、一方向のアップロードのみ。ローカル(IndexedDB)が常に正。**

アップロードするもの:
- ユーザープロフィール
- 公開を選択した目安プロファイル
- 日次の練習集計(時間・日数)

アップロードしないもの:
- 録音音声
- セッションの生データ(フレーム列)
- リードの個体番号・開封日

この方針により、**双方向同期の競合解決が丸ごと不要**になる。

## 10. 既存コードへの影響範囲

デザイン改修が別セッションで進行中のため、影響を最小に抑える。

| 箇所 | 影響 |
|---|---|
| 計測タブの画面 | **変更なし** |
| 目安プロファイルの構造 | **変更なし**。取り込んだものは通常のプロファイルとして保存する。由来を示す `sourceKind: "community"` を足すのみ(既存コードは `Array.isArray()` で未知フィールドを安全に扱う実装になっている) |
| 計測タブのライブ解析 | **累積カウンタを1つ足すのみ**(§4.4 の練習時間)。画面表示・計測ロジックには触れない |
| 新規追加 | コミュニティタブ、認証層、同期層 |

**唯一の既存コード変更点は練習時間の累積カウンタ**であり、これは非表示のロジックのため、進行中のデザイン改修と衝突しない。

## 11. リスクと対応

| リスク | 対応 |
|---|---|
| 環境差で他人の目安が噛み合わない | §3 の平行移動。加えて端末クラス・練習場所での絞り込み |
