# 便AH 仕様凍結: アイコンに任意の写真を使えるようにする

2026-09-23 統括が凍結。本人の裁定ずみの決定だけを書く。**ここに無いことを実装しない。**

前提として便AG（通報の入口を裏の末尾へ）は配信済み。本人は Firebase コンソールで
Blaze 有効化 / Storage バケット作成 / Cloud Vision API 有効化 / 予算アラートを済ませている。

---

## 決定0: 何を作るのか（一文）

いまの「絵柄24種 × 色10」に加えて、**自分の写真1枚**をアイコンにできるようにする。
写真は保存の最中に自動判定を通り、通らなければ保存されない。

---

## 決定1: 選ぶ画面は 5列 × 5行

いまは 6列 × 4行 = ちょうど24個（`CommunityTab.jsx` のアイコン格子）。
写真枠を足すと25個になり、最後の行に1つだけ残る。

**列を6→5にする。5 × 5 = 25 でちょうど埋まる。** 絵柄は1つも捨てない。
写真枠は**格子の先頭（左上）**に置く。

- マスは 375px の画面で約50px → 約62px に広がる。`--tap-min` 44px への余裕が増える。
- `minmax(0, 1fr)` は**外さない**。外すと格子が画面より広くなり、ページ全体を押し広げる
  （過去に色の行が476pxになり、375pxの画面でニックネーム欄が画面外へ出た事故がある）。
- 写真枠の見た目は、他のマスと同じ器に「写真」の意味の絵柄1つ。
  **選択中の表し方は既存のマスと同じもの**を使う。新しい状態表現を発明しない。
- 既に写真を設定している人は、写真枠に**その写真の縮小**が出る。

## 決定2: 写真を選んでいる間、背景色の行は消える

丸く切り抜くので、10色の地は写真の裏に隠れて意味を持たない。
絵柄を選び直したら、色の行は戻る。

## 決定3: 「確認中」の状態は作らない（本人指示）

> 「確認中にするのやめられませんか？　他のアプリでそんなことになっているのはみたことないので体験の低下を招きます」

判定を**保存したあと**ではなく**保存の最中**に行う。流れはこれだけ:

1. 写真を選ぶ
2. 端末で正方形に切り、256px、WebP に書き直す（ここで EXIF が消える）
3. 送る（保存中の待ちを出す。30KBの画像なら1秒弱）
4. 通れば自分のアイコンになる / 通らなければ**何も変わらず**、本人にだけ理由が出る

**保留の状態も `status` の持ち回りも作らない。** 他人が中途半端な状態を見ることは無い。

失敗の文言は既存の調子に揃える（`FeedbackSheet` の `SEND_ERROR` と同じ系統）。
- 判定で落ちたとき: 「この写真は使えません。別の写真をお試しください。」
- 通信で落ちたとき: 「送信できませんでした。電波の良いところでもう一度お試しください。」

## 決定4: 絵柄に戻す導線は作らない

格子で絵柄を選び直せば戻る。「写真をやめる」ボタンは**作らない**。
（説明文・要素は減らす方向、という本人の好みに従う。）

## 決定5: アイコンをタップすると写真が大きく出る（本人指示）

> 「画像タップしたらそのまま画像大きく表示するようにしてもう一度任意の場所タップで戻るようにして」

- **そのまま大きく出す。** 間に選択肢のシートを挟まない（案Bの小シートは不採用）。
- 戻るのは**画面のどこをタップしても**。閉じるボタンは置かない。
- Escape でも閉じる。既存のシートの作法に合わせる。
- **写真のときだけ**。絵柄はベクターなので拡大に意味が無く、タップしても何も起きない。
- 拡大できる場所は次の2つだけ:
  - 人物紹介シートの**裏（プロフィール面）**のアイコン
  - マイページの自分のアイコン
  表（音のデータ面）の名前の行は**いままでどおり行全体がプロフィールへの入口**なので触らない。
  順位などの一覧の行も触らない（行全体がその人を開く）。

## 決定6: 写真はサーバの関数だけが書ける

`users/{uid}` に写真の場所を持つ。**クライアントからは写真を「消す」ことしかできない。**
値を入れられるのは判定を通した Cloud Functions だけ（Admin SDK なのでルールを迂回する）。

こうすると「判定を通っていない写真が載る」経路が**構造上存在しない**。
`firestore.rules` は「クライアントの写真の書き込みは null のみ許す」と書く。

### 【2026-09-23 統括が検収で受け入れた逸脱】

凍結の文は「クライアントの写真の書き込みは null のみ許す」だったが、**字義どおりに
`request.resource.data.photo == null` と書くと、写真を持っている人のアプリが
何も書けなくなる。** ルールが見るのは「今回変えたキー」ではなく**書いたあとの
ドキュメント全体**なので、公開スイッチを触る・練習記録を足す・絵柄を変える、の
どれをしても photo にサーバが入れた値が載ったまま評価され、全部拒否される
(罠の目録の「任意キーの存在ガードを忘れて保存が全滅した」と同じ形)。

実装は「**キーが無い / null / いま載っている値とまったく同じ**」の3つだけを通す。
クライアントが**新しく入れられる値は null だけ**なので、
「判定を通っていない写真が載る経路が構造上存在しない」という決定6 の性質は保たれる。
あわせて `photo` は `hasOnly` にだけ置き `hasAll` には置かない(任意キー)。

**また、置き換え(`setDoc`)が写真を落とさないよう、`saveProfile` は練習記録と同じ
1回の読みで写真を持ち越す。** 落とすとクライアントからは二度と戻せない
(値を書けるのはサーバの関数だけなので)。統括が検収で、持ち越しの行を消す変異を
打って `accountRepo.test.js` の1件が落ちることを確認済み。

## 決定7: 上限はルールで縛る（青天井にしない）

`storage.rules` で:
- 置ける場所は自分の uid の下だけ
- 1人1枚
- サイズ上限（256px の WebP に対して十分な余裕を見た固定値）
- `image/webp` のみ

## 決定8: 通報の理由を2つ足す

`REPORT_REASONS` に「アイコンの写真が不適切」「他人が写っている」を追加。
**`firestore.rules:396` の写しも同時に直す**（`report.test.js` が同期を検査している）。

## 決定9: 消すときは写真も消す

- アカウント削除 → Storage の写真も消す
- 「公開」オフ → 写真は残るが他人から見えない（プロフィール全体と同じ扱い）
- 運営が剥がせる経路を用意する（通報の対応に要る）

## 決定10: 今回やらないこと

- **50人の上限（`DIRECTORY_LIMIT`）には触らない。** 一度に変える面を増やさない。
- ページ送りは別件。
- 写真の切り抜きの自由度（回転・拡大縮小の作り込み）は最小でよい。正方形に切れれば足りる。
