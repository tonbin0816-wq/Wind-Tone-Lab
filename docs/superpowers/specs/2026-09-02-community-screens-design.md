# コミュニティの残り3画面(データ・順位・シェア)の設計

**位置づけ:** `2026-08-27-community-tab-design.md` の §3〜§6 を、実装できる粒度まで詰める文書。
計画2(目安の公開・検索・取り込み)は既に書いてあるので、**この文書はその上に乗る決定だけ**を扱う。
ここで決めたことをもとに計画3(順位)と計画4(シェア・コホート平均)を書く。

**この文書が答える問い:** 3画面が同じ道具を使うために、何を先に決めておく必要があるか。

---

## 0. 3画面の関係

3つは独立した機能ではない。**同じ「条件で人を絞る」仕組みの上に、違う見せ方が乗っている。**

| 画面 | 絞った人たちに対して何を見せるか | 読むもの |
|---|---|---|
| データ | 指標の平均(コホート平均)と、個人の目安の一覧 | `users` + `ideals` |
| 順位 | 練習日数の多い順 | `users` |
| シェア | 機材の内訳 | `users` |

つまり**`users` を条件で絞って読む処理が3画面の土台**で、そこだけは1つの実装を共有する。
別々に書くと、同じ絞り込みが3通りの挙動をする画面ができる(本人の指摘
「同じ粒度の条件抽出が上と下で二つある」は、まさにこれが設計上そろっていなかったことの表れ)。

---

## 決定1: サーバ側の集計(Cloud Functions)を使わない

**なぜ問題になるか。** 順位もシェアも「全員ぶんを数える」処理なので、素直に作るなら
サーバ側で集計したくなる。だが Firebase で Cloud Functions を使うには
**Blaze プラン(従量課金・クレジットカード登録)への切り替えが必要**で、無料枠では動かない。

**採る解: 3画面とも、クライアントが公開ユーザーを読んで自分で集計する。**

- 順位・シェア・コホート平均のすべてを、`users` の公開ドキュメントを読んで画面側で数える
- 読む件数には上限をかける(下記「50件の頭打ち」)
- **カードの登録は不要。無料枠のまま動く**

**なぜこれで足りるか。** いま利用者は0人で、当面は多くて数十人。数十件のドキュメントを
読んで数えるのは、通信量でも計算量でも問題にならない。存在しない規模のために
カードを登録して基盤を増やすのは、costだけが先に立つ。

**いつ移すか(この行を消さないこと)。** 次のどれかが起きたら、計画5で Cloud Functions へ移す。

- 公開ユーザーが **50人を超えた**(頭打ちで順位が正しくなくなる。下記参照)
- 順位の改ざんが実際に起きた(下記「決定3」の受け入れたリスクが現実になった)
- 一覧の読み込みが体感で遅くなった

**50件の頭打ちとは。** クライアント集計は「上位50件を読んで数える」形になるので、
51人目以降は集計に入らない。順位は `orderBy` があるので上位50位までは正しいが、
**シェアとコホート平均は「50人ぶんの標本」になる**。これは嘘ではないが全数ではないので、
画面に **「上位50人ぶんの集計です」と書く**。黙って一部だけ数えるのが一番悪い。

## 決定2: 条件行は1つの部品にする(楽器 × ジャンル × 属性)

本人の指摘のとおり、条件の選び方が画面ごとに違うと使い方を覚え直すことになる。

**仕様:**

- 3つの掛け算に固定する: **楽器種別 × ジャンル × 属性**
- 3つとも「指定なし」を選べる。既定は3つとも指定なし
- 楽器種別だけは単一選択(`soprano`/`alto`/`tenor`/`baritone`)。
  絞り込みの対象が「その種別の機材・その種別の指標」であり、複数種別を混ぜると平均の意味が壊れる
- ジャンルと属性も単一選択。**複数選択にしない** ── 「クラシック または ジャズ」の平均は
  誰の目安にもならない。掛け算の意味を保つ
- 見た目は1行に3つのプルダウン。**カードで囲まない**(本人裁定)
- データ・順位・シェアの3画面すべてで同じ部品を同じ位置(上部1行)に置く

**絞り込みはクライアントで行う。** Firestore のクエリでは
`isPublic == true` と並べ替えだけを指定し、楽器・ジャンル・属性の一致は読み込んだ後に
JavaScript で判定する。理由は2つ:

1. 3条件の組み合わせごとに複合インデックスが要り、組み合わせ数だけ増える
2. `genres` は配列で、`array-contains` は1クエリに1つしか使えない

50件の頭打ちの中で絞るので、**「条件を絞ったのに0人」が起きうる**。
そのときは「条件に合う人がまだいません」と出す。0人を0で割って NaN を描かない。

## 決定3: 順位のデータの持ち方

### 何を数えるか

**練習日数。** 回数や音数ではない(本人裁定: 回数はチートしやすい)。
1日に何時間吹いても1日と数えるので、水増しの利得が小さい。

### どこに置くか

`users/{uid}` に `stats` を足す。**新しいコレクションを作らない**(順位・シェア・
コホート平均がすべて同じ1回の読み込みで済む)。

```js
stats: {
  daysThisWeek: 3,      // 今週(月曜始まり)に練習した日数
  daysThisMonth: 12,    // 今月
  daysThisYear: 140,    // 今年
  daysAll: 320,         // 累計
  computedAt: "2026-09-02T12:34:56.789Z", // この値を計算した時刻(端末の時計)
}
```

`computedAt` は飾りではない。**下の「古い値の扱い」がこれ1つに乗っている。**

### いつ書くか

アプリを開いたときに1回、ローカルのセッションから数え直して書く。
練習のたびには書かない(書き込み回数が無駄に増える)。

### 古い値の扱い ── ここが一番壊れやすい

**問題。** 先月たくさん練習して、その後アプリを開いていない人がいる。
その人の `daysThisMonth` は**先月の値のまま**なので、今月の順位に先月の成績で並ぶ。

**解: 読む側が `computedAt` を見て捨てる。**

- 「今週」の順位 → `computedAt` が今週の中にある人だけを数える
- 「今月」→ `computedAt` が今月の中にある人だけ
- 「今年」→ 同様
- 「すべて」→ `daysAll` は期間に依存しないので捨てない

こうすると「今月ずっと開いていない人は今月の順位に出ない」。これは正しい。
今月の練習が0日なのだから、0日の人として出ないのが実態に合う。

**時計は信用しない。** `computedAt` は端末の時計なので、ずれていれば嘘になる。
未来の日付(受け取った時点より後)は**その場で捨てる**。過去方向のずれは救えないが、
これで「時計を進めて今月に居座る」だけは塞げる。

### 改ざんについて、正直に書いておく

**この設計では、順位の改ざんを防げない。** `stats` は本人のクライアントが書くので、
生の SDK を叩ける人は `daysAll: 99999` と書ける。ルールで止められるのは
「数値であること」「負でないこと」「上限を超えないこと」までで、
**その数が本物かどうかはサーバにしか判定できない**(ローカルのセッションはサーバに無い)。

受け入れる。理由:

- 匿名アカウントの順位を偽って得られるものが無い(賞品も権限も無い)
- 防ぐには決定1で見送った Cloud Functions が要る
- 上限を入れておけば、**桁違いの数字で画面が壊れることは防げる**(見た目の破壊は防ぐ)

上限は `daysAll <= 36500`(100年)、期間つきの3つは
`daysThisWeek <= 7` / `daysThisMonth <= 31` / `daysThisYear <= 366`。
**期間の上限は改ざん対策としてではなく、定義上ありえない値を弾くために置く。**

実際に偽装が起きたら決定1の移行条件に当たるので、そのとき Cloud Functions へ移す。

## 決定4: シェア(機材の内訳)の作り方

読むのは `users` の `gear` だけ。新しいドキュメントは作らない。

### 単品の内訳

条件行で絞った人たちについて、**選んだ楽器種別の** `gear[saxType]` を数える。

- 楽器・マウスピース・リガチャーの3つ、それぞれ別の内訳を出す
- リードは **2026-09-02 にプロフィールの機材へ追加した**(本人裁定)ので、
  楽器・マウスピース・リガチャー・リードの**4種すべて**の内訳を出せる。
  **番手は持たない** ── 番手はセッション側(リードタブ)の情報で同じ銘柄でも日によって変わる。
  ここに入れると同じ銘柄の人が番手ぶんに割れ、内訳が実態より細かく散る
- 数え方は `brand` と `model` の組。`model` が null の場合(= その他)は
  「その他」として1つにまとめる
- **`null` は「未選択」として、その他とは別に数える。** 2026-09-02 に機材は必須になったが、
  それ以前に保存されたドキュメントと、ルールを直接叩いた書き込みには null が残る。
  未選択を「その他」の票に混ぜると、内訳が実態より「その他」に寄る

### 人気の組み合わせ

条件行とは別に、**何項目の組み合わせを見るかを選ぶ**(本人裁定)。

| 選択 | 組み合わせ |
|---|---|
| 2項目 | マウスピース × リード |
| 3項目 | 楽器 × マウスピース × リード |
| 4項目 | 楽器 × マウスピース × リガチャー × リード |

4項目すべてが `gear` に揃ったので、**この表のまま作れる**。
数え方は単品の内訳と同じで、組にしてから数えるだけ。

## 決定5: コホート平均(みんなの平均)の出し方

条件行で絞った人たちの `ideals` を読み、**音名ごとに平均する**。

- 平均するのは重心と HNR と音程。**音量は平均しない**(設計書 §3: 共有しない)
- 平行移動してから平均する。移動量の求め方は計画2の Task 1 と同じ関数を使い、
  **書き直さない**
- 基準は「その人たち全体の中央値」ではなく、**見ている本人**に合わせる。
  自分の線が動かないので、他人の線がどちらへずれているかがそのまま読める
- 平均に使った人数を必ず出す(「42人のデータ」)。**3人未満なら平均を出さない** ──
  少数の平均は個人の特定に近づき、かつ平均として意味が無い

`ideals` は `ownerUid` を持つので、絞り込んだ uid の一覧から
`where("ownerUid", "in", [...])` で引く。**`in` は一度に30件まで**なので、
50人ぶんは2回に分けて引く。

## 計画2に残っていた宿題への裁定

### 宿題1: `adoptionCount` の置き場所 → **作らない(先送り)**

決定1でサーバ側の集計を持たない以上、採用数を誰かが正しく数えることはできない。
本人が書けば偽れるし、計画2の `setDoc` 全置換とも衝突する。

**票の表示と「採用数の順位」は作らない。** 並べ替えは `updatedAt` の新しい順にする。
順位は練習日数の一本でいく(本人裁定とも一致する)。
Cloud Functions へ移すとき(決定1の移行条件)に、案Aで足す。

### 宿題2: `notes` の中身の型 → **読む側で守る**

ルールでは「各音の値が数値であること」を書けない(繰り返しが無い)。
Cloud Functions も使わないので、書き込み時点で弾く手が無い。

**採る解: 読んだ直後に数値でないものを落とす。**

- コホート平均も個人の目安の表示も、`sanitizeNotes` と同じ検査を**読む側でも通す**
- 数値でない音は、その音だけ落とす(ドキュメントごと捨てない)
- 落とした結果その人の有効な音が3つ未満になったら、その人を平均から除く

**書き込みを塞ぐ代わりに、壊れた値が画面へ届かないようにする。** 完全ではない
(壊れた値は Firestore に残る)が、他人の画面を壊すことは防げる。これが
Cloud Functions 無しで到達できる上限である。

## Firestore ルールの変更 ── 1回にまとめる

**ルールの公開は本人の手作業なので、変更は溜めて一度に出す。** 3画面ぶんを個別に出すと
3回作業させることになる。計画3と計画4のルール変更は**同じ1回**で公開する。

変更点は3つ:

1. `users` に `stats` を足す(12キー → 13キー)。`hasAll` / `hasOnly` の両方を直す
2. `stats` の中身の検査: 4つとも `is int` かつ `>= 0`、上限は決定3の値
3. `users` の一覧を開ける: `allow list: if resource.data.isPublic == true`

**3 は「公開している人だけが一覧に返る」ことを意味する。** 一覧の規則は
返る1件ごとに評価されるので、非公開の人が1人でも当たるとクエリ全体が失敗する。
つまりクライアントは必ず `where("isPublic", "==", true)` を付けねばならない。
**付け忘れると全件失敗する。**これは事故ではなく、そう設計している ──
「うっかり非公開の人まで読む」が起きない形になっている。

`ideals` の `list` は計画2で既に開く。ここでは触らない。

## 決着した論点(2026-09-02)

### リード → プロフィールの機材に追加した(実装済み)

`gear` を6キーから8キーへ広げ、`reedBrand` / `reedModel` を足した。
入力は他の3つと同じ部分一致の検索。`REED_CATALOG` は13銘柄50型番。
**番手は持たない**(理由は決定4)。

**通称では検索できない。** 銘柄はカタカナで引ける(「バンドーレン」「レジェール」)が、
型番は英字だけなので「青箱」と打っても0件になる。本人裁定「製品名は正式名称」に従って
保存も表示も `Traditional` にしてあるが、**探すときの入口としての通称**は別の話で、
いまの仕組み(ブランド別名しか無い)では拾えない。型番の別名を足すかは未着手。

### 順位に出す情報 → 画面案のまま

`design/community-tab-proposals.html` の順位カードに出ているものを採る。

| 出すもの | 出どころ |
|---|---|
| 順位の数字 | 並べ替えの結果 |
| アイコン(絵柄 + 背景色) | **プロフィールに未実装。下記参照** |
| ニックネーム | `users.nickname` |
| 属性 ・ 歴N年 ・ ジャンル | `position` / `startYear` から計算 / `genres[0]` |
| 練習日数 | `stats`(決定3) |

- 上位3件はカードを独立させ、アイコンに順位の環を回す(台の高さには頼らない)
- 自分の行は一覧の最下部に「あなた」のバッジ付きで固定する。**圏外でも自分は必ず見える**
- 人物紹介(タップして開く画面)の練習日数は**累計**。順位は期間で切り替えるものだが、
  素性の紹介としては累計のほうが読める

## 未決事項(着手前に本人へ確認すること)

### 未決事項1: アイコンがプロフィールに無い

順位のカードもコホート平均の一覧も、画面案は**アイコン(絵柄 + 背景色)**を出している。
だが `users` にその項目が無い。いまのプロフィールは14キーで、アイコンは含まれない。

作るなら、プロフィールに2つ足すことになる:

- `icon`: 絵柄の識別子(既製の24種から1つ)。**画像のアップロードはしない**
  (2026-08-28 に本人が選択済み。アップロードは審査・モデレーション・保管費が一気に増える)
- `iconColor`: 背景色(既製の10色から1つ)。10色とも白地に対し 4.5:1 以上を実測済み

`design/DESIGN-SYSTEM-community-addendum.md` に色の値と根拠が既にある。
**足すなら、いま溜めている Firestore ルールの変更と同じ1回で出せる。**
後から足すと、ルールの公開作業がもう1回増える。
