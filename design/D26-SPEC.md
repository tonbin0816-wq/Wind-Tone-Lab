## §1 いま分かっていること（推測と事実を分ける）

### 1.1 事実（コードから読める）

外周の光は SVG で**マスク3枚の入れ子**として作られている（`PitchRing`）:

```
<g glowGroupRef mask=falloff opacity="…">     ← rAF が毎フレーム書き換える
  <g glowBreathRef>                           ← CSS の ficus-ring-breathe が opacity を常時動かす
    <g mask=smooth><rect 460×460(SVG単位) fill=光の色 /></g>
    <g mask=grainy><rect 460×460(SVG単位) fill=光の色 /></g>
```

- マスクの矩形は `RING_GLOW_RECT_SIZE = 460 * (RING_VB/300)` の正方形。**環の SVG より大きい**
- rAF は `opNum = ringGlowOpacity(raw, 1, glowCents)` を出し、`op !== lastGlow` のとき
  最外の `<g>` の `opacity` を書く。**`glowCents` は生の音程**なので、
  **±4¢（`RING_GLOW_NEAR_CENTS`）の内側では毎フレーム値が変わり、毎フレーム書く**
- ±4¢ の**外**では `opNum` が 0 に張り付くので**書き込みが起きない**

### 1.2 症状との一致

本人の報告は一貫して「**±4 の外は滑らか / 内は変わらず**」。
上の構造では、**書き込みが起きる範囲と症状が出る範囲がぴたり一致する**。

### 1.3 仮説（**まだ実機で確かめていない**）

**SVG のマスクは合成器（GPU）に載らない。** マスクの掛かった部分木は、
不透明度が変わるたびに CPU でラスタライズし直される。
ここは 460×460（SVG 単位）にマスク3枚。**1フレームぶんの描き直しが重い。**

呼吸（`ficus-ring-breathe`）も同じ部分木の opacity を動かすので、
**±2¢ の内側では、重い描き直しが常時走り続ける**。

**これは仮説である。** JS からは style 再計算・レイアウト・ペイント・合成が
構造的に見えない（**罠17**）ので、Chrome の計器では確かめられない。
**確かめられるのは本人の目だけ。** ただし下の直しは、仮説が外れていても
**描き直しの量が減ることは確実**（マスク3枚が0枚になる）なので、進めてよい。

## §2 直し（凍結）

### 2.1 光を SVG から出し、**1枚の要素 + 1本のグラデーション**にする

**マスクを使わない。** 光の最終的なアルファの形は、いまの実装の純関数から
**閉じた式で出せる**:

- 内側 = `1 - ringGlowRampAt(r)`
- 外側 = `ringGlowRampAt(r)` を**上に重ねる**（source-over）
- 重ねた結果 = `(1-ramp) + ramp·(1-(1-ramp))` = **`(1-ramp) + ramp²`**
- それに減衰マスク `ringGlowAlphaAt(r)` が掛かる

したがって

```
α(r) = ringGlowAlphaAt(r) · ( (1 - ringGlowRampAt(r)) + ringGlowRampAt(r)² )
```

**この式を、実装の純関数から出したグラデーションの停止点に焼き込む。**
D-23d で呼吸を CSS のキーフレームに写したのと同じ手順（**定数を書き写さない**）。

- 停止点の数は、**折れ線で近似したときの最大誤差が 8bit の量子化（1/255）より下**になるまで増やす
- **期待値は `ringGlowAlphaAt` / `ringGlowRampAt` から出す**（罠3。数値を書き写した検査は恒真）

### 2.2 明るさと呼吸の掛け算

合成の不透明度 = **明るさ（rAF が書く）× 呼吸（CSS が動かす）** の形は**変えない**。
入れ子は**2段まで**。マスクを持たないので、どちらの opacity も合成器の仕事になる。

### 2.3 置き場所

環の SVG の**奥**（いまと同じ重なり順）。位置と大きさは
`RING_GLOW_RECT_MIN` / `RING_GLOW_RECT_SIZE` / `RING_GLOW_R_MAX` / 環の中心から出すこと。
**新しい寸法の定数を発明しない。** 拡大率が変わっても付いてくる形（%）で書く。

### 2.4 明るさの書き込みを 8bit に量子化する

`op = opNum.toFixed(4)` は **1/10000 刻み**。画面に出るのは 8bit なので、
**1/255 より細かい差は1pxも変わらない**。量子化して、**変わったときだけ書く**形は
いまのまま維持する（`op !== lastGlow`）。

**これは §2.1 の代わりではなく、両方やる。** 書き込みの回数を減らすのと、
1回あたりの費用を下げるのは別の話。

## §7 裁定（統括 2026/09/02）── **§2.1 と §3 の食い違いについて**

実装から「§2.1 と §3 は同時に満たせない」と報告が上がった。**正しい指摘で、間違っていたのは §3（と §2.1）の物差しのほう。**

### 7.1 何が起きたか

- **§2.1** は「連続な式との折れ線誤差が 1/255 未満になるまで停止点を増やせ」と書いた
- **§3** は「変更前との画素差 1/255 以下」と書いた
- ところが**変更前の44段そのものが、連続な式から既に 2.30/255 離れている**
  （本人が選んだ試作 案③ の形。近似であって理想曲線ではない）
- したがって停止点を増やすと式には近づくが、**本人が見ている見え方からは遠ざかる**
  （88段で 2.18/255、256段で 2.16/255 変更前から離れる）

**§2.1 は「理想の式に合わせろ」と書いてしまったが、守るべきは「本人が見ている光」だった。**
実装は44段（同じ半径）を選んで §3 を優先した ── **その判断が正しい。**

### 7.2 §3 の 1/255 も、測っている物が違った

実装の報告は最大画素差 **3/255**。統括が**独立に計算し直した**結果:

```
旧の合成アルファ（内側の上に外側を source-over → 減衰を掛ける、いずれも旧の停止点から）
  vs 新の1本グラデーション（同じ44段）
    最大差   0.0366/255      （半径の割合 0.792）
    平均ずれ -0.00205/255    （系統的な明暗のずれは無い）
    0.5/255 を超える点 0 / 40001
```

**光そのものは実質同一。** 3/255 は **8bit の中間バッファの丸め**であって、光り方の変化ではない:

- マスク3枚 = 合成のパスが3回 → そのたびに 8bit へ丸める。**その丸めを無くしたのが今回**
- 丸めが変われば画素は必ず動く。実装が示した「変更前の2枚を**重ね順だけ入れ替えた**
  （解析的に同一の）版でも 1/255 出る」は、この床の存在の良い裏取り
- 差の**符号が半径ごとに ± に振れる**（系統的な明暗のずれではない）。上の平均 -0.002/255 が同じことを言う

> **【訂正 D-28】この行の「± に振れる」は、画素差については正しいが、
> アルファの形については誤り。** 独立審査の指摘を受けて数え直したところ、
> 新 − 旧 の符号は **正 7156 / 負 2767 / 完全一致 30078**（40001点）で
> **正に偏っている**。`H(x) = (1-x) + x²` は凸なので折れ線近似は必ず上に出る
> （`lerp(H(g)) ≥ H(lerp(g))`）── **数学的に必然**で、散らばりではない。
> 大きさが 0.0366/255 なので結論（実質同一）は変わらないが、
> **画素差についての説明をアルファの形にも当てはめてしまっていた。**
> 「符号が振れるかどうか」は丸めか偏りかを見分ける良い指標だが、
> **偏っていても大きさが十分小さければ問題ない**ので、指標は大きさのほう。
- 8.2% の画素が ±1、0.2% が ±2、残りは完全一致

**§3 の「画素差 1/255」は、マスクを外す変更に対しては原理的に満たせない指標だった。**
測るべきは**アルファの形**であって、ラスタライザの丸めではない。

### 7.3 裁定

**このまま進める。** ただし記録に残すこと:

- **合否の指標を「画素差 1/255」から「アルファの形の差」へ差し替える。**
  今後この光を触るときは `0.0366/255`（またはそれ以下）を基準にする
- **§2.1 の「連続な式に近づけろ」は誤り。** 守るべきは**本人が選んだ44段の形**。
  停止点の数と半径を変えないこと（増やすと本人の見え方から離れる）

### 7.4 この周で学んだこと（罠へ）

**「同じに見えること」を画素差で測ると、実装の作りを変えた瞬間に測れなくなる。**
中間バッファの丸めは作りに依存するので、作りを変える修正では**必ず**動く。
比べるべきは**設計上の量**（ここではアルファの曲線）であって、その量を 8bit で
2回丸めた結果ではない。**閾値を決める前に「その数字は何で動くのか」を数えること。**
