## §0 確定した因果と、残る二義性（なぜこの設計か）

10周の切り分けの末、本人の実機で**再現性のある A/B** が取れた:

> **「① 鳴っていない表示にする」を 10秒おきに 2〜3回 オン・オフ → 押すたびに毎回、確実に滑らか⇄カクつきが切り替わる**

確定していること（すべて本人の実機・一次データ）:
- JS の実行時間は犯人ではない（1秒のうち 22.1ms = 2.2%。ピッチ検出 0.45ms/回）
- **状態更新の回数**は犯人ではない（D-21 で 3.00→1.18本/フレームにしても変化なし。
  さらに ① は volumeDb を凍らせないのに滑らか ＝ **毎フレーム級の再レンダー自体は無害**）
- **DOM 書き換えの本数**は犯人ではない（D-22c で帯30個を止めても変化なし）
- 効いた2条件（① / 表示値づくり）の共通点は
  「**毎フレーム変わる値が、React を通って環のサブツリーへ流れ込むのを止める**」こと

残る候補は2つで、**現データでは切り分け不能**:

| 候補 | 根拠 | ①で消える理由 |
|---|---|---|
| **(A) 環サブツリーの毎フレームの vdom 組み直しと差分** | ①の A/B | 値が凍ると vdom が恒等になる |
| **(B) 外周の光の矩形2枚の `fill` 書き換えが誘発する、feTurbulence マスク約1500実画素の再描画** | Fable 検証で「どのスイッチでも fill は止まらない」ことがコードで確定。Step 2（±30¢ 飽和で凍らせる実験）は、音名を消した状態で ±30¢ を保てたか**検証不能**だった | 値が凍ると fill も止まる |

**この仕様は (A)(B) を両方、同じ周で潰す。** どちらも「値が同じなら仕事ゼロ」という
無条件に正しい最適化であり、どちらが真犯人でも直る。**戻す単位を分けるため、コミットは2つに割る**（§8）。

## §1 方針: 環の毎フレーム値は ref + 既存の rAF ループが運ぶ。React には流さない

**根拠となる既存の実例**: `MetroPendulum` の rAF は毎フレーム12属性を直接書いているが、
静音時（滑らか）でも走っている ＝ **rAF からの直接書き込みは安い**ことが実機で証明済み。
走り・外周の光も既に同じ作法（`runPathRefs` / `glowGroupRef`）。**帯・弧・セント文字だけが
React に取り残されていた**。これを揃える。

### 1.1 値の受け渡し

- 解析 tick は、毎フレーム変わる表示向けの値（f0 / 生のセント / sounding）を
  **`setPitch` ではなく共有 ref**（名称例 `pitchDisplayRef`。命名は実装が決める）に書く。
- **React の状態には「音の同一性」だけを残す**: 半音インデックス（音名・オクターブ）と
  sounding の on/off。これらは毎秒数回しか変わらない。音名の文字・到達の呼吸・運指表示は
  この粗い状態から従来どおり React が描く（①実験より、この頻度の再レンダーは無害）。
- `matchedFingering` / `harmonicLevels` / `centroidHz` / `hnrDb` / `volumeDb` は
  **D-21 の同一性安定化のまま触らない**。

### 1.2 環の駆動

- `PitchRing` の**既存の rAF ループ**（走り・光を書いているもの）が、毎フレーム
  `pitchDisplayRef` を読み、**EMA → deg → 帯のグラデーション30ストップ → 弧の `d` →
  セント文字と色 → 光の fill/opacity** を計算して**属性を直接書く**。
- **EMA はこの rAF ループへ移す。** 式は現行どおり `α = 1 − exp(−Δt/τ)`、
  τ は `DESIGN-SYSTEM.md` §1.11 が持つ 60ms（**値も式も変えない**。検査もそこから読む形を保つ）。
  レンダー本体の副作用（StrictMode 二重実行の温床）がこれで消える。
- **書き込みは「値が前回と変わったときだけ」**（走り・光の既存作法と同じ）。
  文字は丸めた後の文字列で比較する。

### 1.3 二重書き手の禁止（この設計でいちばん事故りやすい点）

- rAF が書く節（帯・弧・セント文字・光）は、**React が再訪しない構造**にする。
  React は骨格を初回に描くだけで、以後その内側の属性・textContent に触れない。
  機構は実装が決めてよい（常に等価と答える memo での封印など）が、
  **「同じ属性を React と rAF の両方が書く」状態を作らないこと**。既存の光の opacity は
  現状この二重書きになっており（React :5644 側と rAF 側）、**この周で rAF 単独に一本化する**。
- 弧・帯の `<path>` は**常時マウント**し、消すときは `d=""` を書く（毎フレームの
  マウント/アンマウントを作らない）。見た目は同一。

### 1.4 触ってはいけないもの

- **計測ロジック**（`detectPitchMPM` / `matchFingering` / 録音フレーム / ヒステリシス）は1ビットも変えない。
  tick の中の計測側はそのまま。変わるのは「表示への渡し方」だけ。
- τ=60ms / 抑制 1110ms / **F-47（揺らしても走りは1回だけ）** / reduced-motion の挙動 /
  走り・呼吸の演出のタイミング。
- `will-change` はアプリ全体で禁止（F-106。検査 30.1）。**この周でも使わない。**
- `MetroPendulum`（振り子）には触らない（観測対象。D-22b は起票のまま）。
- 他画面・他タブへの波及ゼロ。

## §2 外周の光: 静的マスク束の事前ラスタ化（候補 B の除去）

- 光の構造は「色付き矩形 × 静的マスク3段（減衰・傾斜・feTurbulence の粒）」。
  **毎フレーム変わるのは fill と opacity だけで、マスク束は完全に静的**。
- 静的なマスク束を**初回に一度だけラスタ化**し（そのブラウザ自身に描かせて取り込む＝
  見た目はそのブラウザの feTurbulence 描画と構築的に同一）、以後の毎フレームは
  「小さな合成」だけで済む形にする。機構（offscreen canvas / 画像マスク等）は実装が決める。
- **DPR を考慮**すること（iPhone は 3）。初回ラスタ化が終わるまでの1〜2フレームは
  光を出さなくてよい（無音から始まるので見えない）。
- reduced-motion・光の段（合った/近い/それ以外）・呼吸との関係は現行の挙動を保つ。
- **見た目の同一性はピクセル比較で示す**（現行構造と新構造を同じ値で描いて突き合わせ）。

## §3 診断パネル（`#metro-diag`）の扱い

- **残す**（本人の最終確認に使う）。「① 鳴っていない表示にする」は、新構造では
  **rAF の更新側を止める**形に配線し直し、**同じ A/B が引き続きできる**ようにする。
- 役目を終えたスイッチ（帯の色目盛 等、React 経路前提のもの）は**畳んでよい**。
  畳んだら板の文言と検査を追随させる。counters（測り直し・⑦）は残す。
- 恒久機能ではない旨の扱いは従来どおり（原因確定後の撤去は別途本人裁定）。

## §4 検査

- **「rAF の更新が止まると環が凍る」変異が KILL されること**（更新の配線が生きていることの担保）。
- **「React と rAF が同じ属性を書く」状態に戻す変異が KILL されること**（§1.3）。
- EMA の式・τ は §1.11 から読む既存の検証34 を**移設先でも成立**させる
  （F-47 系・走り直しの境目 990ms・速い揺らしの吸収、すべて緑のまま）。
- **表示のパリティ**: 同じ入力列に対して、旧経路と新経路で「画面に出る値」
  （セント文字・音名・帯/弧/光に書かれる属性値）が一致することをハーネスで突き合わせる。
- 検査名は実際に検証している内容しか名乗らない（罠1）。**「滑らかになった」とは
  どこにも名乗らせない**（実機でしか判定できない。罠15）。
- 変異試験は複製ツリーで単独逐次。「KILL されては困る変異」も必ず当てる。
