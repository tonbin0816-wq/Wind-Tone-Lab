# Ficus デザイン方針

このドキュメントは「デザイン改善フェーズ」の唯一の引き継ぎ資料。
実装セッションの文脈（メトロノーム実装・マイクバグ等）は引き継がず、ここに書かれたものだけを前提にする。

最終更新: 2026-07-24

## 0. このフェーズの目的

**視覚的な使いやすさと、楽しめるかを追求する。** 機能追加ではない。

ユーザー本人の言葉:
> 「このアプリの今最大の課題はデザイン性です」
> 「いかにこのアプリユーザーを視覚的に使いやすいか、楽しめるか、を追求します」

---

## 1. 決定済みの方向性: 「育てる × 静けさ」

複数案から本人が選択した方向。**この2つは対立せず、同じ絵の両面**として扱う。

### 育てる（Ficus）
アプリ名は観葉植物、アイコンは葉。しかし中身は dB・HNR・スペクトル重心・ピボット集計という完全な計測器で、**名前と中身がズレている**。このズレは欠点ではなく未使用の資産。

練習アプリの本質的課題は「続くかどうか」。楽しさを作る最短路は **蓄積が目に見えて育つこと**。名前が既に「育てる」と言っているのに、データタブは折れ線グラフしか返していない。

→ **計測器としての正確さは一切捨てず、報酬系だけを植物のメタファで載せる。**
→ データタブを「反省する場所」から「見に行きたい場所」に変える。

### 静けさ（余白）
派手なゲーミフィケーションにはしない。観葉植物は静かに育つ。
和の「間」。要素を減らし、余白と時間の流れで見せる。練習という行為の邪魔をしない。

### やらないこと
- 賑やかなバッジ・紙吹雪・レベルアップ演出などの直接的ゲーミフィケーション
- 計測精度を犠牲にする装飾

## 2. このアプリ固有の最重要原則: 二面サーフェス設計

**決定的な特殊性**: ユーザーは両手で楽器を持ち、口にマウスピースを咥え、スマホは譜面台の上（目から50cm〜1m）にある。**普通の「手に持つスマホアプリ」ではない。**

ここから2種類の画面を明確に分けて設計する。

| | 演奏中サーフェス | 合間サーフェス |
|---|---|---|
| 該当 | チューナーメーター、振り子、音名、これまでの音 | 詳細分析、リード管理、データ、設定 |
| 視距離 | 1m・**チラ見・周辺視野** | 手元・じっくり |
| 手 | **塞がっている**（操作できない） | 自由 |
| 設計原則 | 極大・色と動きで伝える・**文字を読ませない** | 情報密度を上げてよい |
| 現状評価 | メーター自体は良い。但し12pxラベルが混在し原則が徹底されていない | 概ね妥当 |

**現状の問題**: 全画面が「手元で読む」前提の12px基調になっている。
**打ち手**: 演奏中サーフェスだけ思い切って別の設計言語にする（音名をさらに巨大に、ラベルを消す、色と位置だけで判断できるようにする）。変更範囲が限定的なので安全かつ効果が大きい。

## 3. 進め方（順序に意味がある）

1. **見える化を先に直す**（§6）。これが無いと以降すべて手探りになる。
2. **モックアップで方向を決める。** コードを触らずHTMLで複数案を作り、**見て選んでもらう。**
   - 重要: 本人は以前「こうしたい、というのがないのが現実です」と明言している。
   - **仕様を聞くのではなく、見せて選んでもらう**のが正しいアプローチ。抽象的な質問をしない。
3. **選んだ方向を1画面ずつ実装。** その画面に必要な範囲だけトークン化する。
4. 順番: **計測タブ（チューナー） → データタブ → リードタブ**（滞在時間と効果の順）
   - 計測タブ = 最も長く見る画面
   - データタブ = 「育てる」の主戦場
   - リードタブ = 管理機能、優先度低

叩き台として `design/current-ui-mockup.html` が既にある。

## 4. 現状の資産棚卸し

### 4.1 CSS変数（`src/index.css`）— 既にあるもの
```
--font-jp     : OS標準和文（iPhoneではヒラギノ）
--font-num    : Space Grotesk（数値・英字）
--font-serif  : Instrument Serif（音名・リード番号）
--fs-xs 12px / --fs-sm 13px / --fs-md 15px / --fs-lg 18px
--fs-xl 22px / --fs-2xl 28px / --fs-hero 46px
```
ユーティリティ: `.jp-label`（字間+0.02em）, `.num-tight`（字間-0.02em）

### 4.2 色 — **変数化されていない（最大の負債）**

`src/App.jsx` に **ユニーク約45色 / hex直書き約470箇所**。すべてインラインstyle。
色・余白・角丸に変数は1つも無い。

意味: 「全体を温かみのある色に」「角丸を統一」「ダークモード」はどれも**470箇所の書き換え**になる。
逆に言えば、ここを通せば以後のデザイン変更は**数値を数個変えるだけ**になる。

現状の色を意味別に整理したもの（トークン設計の出発点）:

| 役割 | 現状の値 |
|---|---|
| プライマリ紺 | `#174585`（最頻出） |
| 最濃テキスト | `#121F32` |
| 副テキスト | `#435266` |
| ミュートテキスト | `#8D95A1`, `#A6AEBA` |
| 罫線・境界 | `#E9ECF0`, `#ECEEF1`, `#EEF1F4`, `#C3CAD3`, `#D5DAE0`, `#DDE2E8` |
| 背景 | `#F6F7F9`(ページ), `#FFFFFF`(カード), `#EDEFF3`(サブタブ), `#F3F5F7` |
| 紺のティント | `#EAEFF5`(選択), `#B9C9E4`, `#9DB3CC`, `#9DB3D6`, `#D9E1EC`, `#F3F6FA`, `#7FA0CE` |
| 良い（緑） | `#16A34A` / 背景 `#E8F6ED` |
| 注意（橙） | `#D97706` |
| 悪い・録音（赤） | `#DC2626` / 背景 `#FEF2F2` |
| 警告バナー | `#FDF0E1`, `#F0D9B8`, `#8A5A00` |
| グラフ線 | `#8FB4FF` |

**要注意の不整合**: リード比較の系列色が
`#7C3AED`(紫) `#0891B2` `#DB2777`(桃) `#65A30D` `#EA580C` `#4F46E5` `#0D9488` `#9333EA`
と、紺基調のアプリとまったく別の視覚言語（Tailwind既定色系）になっている。統一対象。

### 4.3 ピッチ判定の色（機能的意味を持つ）
`pitchBarColorRGB(cents)` が |¢| に応じて補間: 緑`rgb(22,163,74)` → 橙`rgb(217,119,6)` → 赤`rgb(220,38,38)`
（0¢=緑 / 13¢=橙 / 30¢以上=赤）。**意味を持つ色なので変更は慎重に。**

## 5. 画面インベントリ

すべて `src/App.jsx`（約6000行・377KB の単一ファイル）。インラインstyleのみ。

```
下部ナビ 3タブ
├── 計測 (MeasureView)
│   ├── 上部設定行: リード選択 / 奏者 / 楽器種別 / 基準Hz / メトロノームアイコン
│   ├── [演奏中] 音名大表示(84px, serif) + PitchMeter(±50¢)
│   ├── [演奏中] これまでの音 (PitchDeviationLine, 直近30秒)
│   ├── 録音 / 録音をアップロード
│   ├── 詳細トグル(最下部) → 倍音構成 / 音量 / 重心 / HNR / 計測下限dB / 基準
│   └── メトロノームパネル: 振り子 + 拍子 + START/STOP + テンポ + コンパクトメーター
├── リード (ReedsTab)  ── 子タブ: 登録 / 比較（左右スワイプ）
│   ├── 新規登録（銘柄・番手・使用開始日 / 1枚 or まとめて）
│   ├── 登録済みリード一覧（箱→個体の2階層・ドラッグ並び替え・★評価）
│   └── 個別詳細: 総評(ダイヤル) / 厚さ / バランス / メモ / 測定データ
└── データ (AnalysisLabView) ── 子タブ: My Data / 分析（左右スワイプ）
    ├── My Data: 推移グラフ / 平均指標カード / セッション一覧
    └── 分析: PIVOT クロス集計（フィルター・縦軸・横軸・指標）
```

主要コンポーネント: `PitchMeter` / `PitchDeviationLine` / `MetronomePendulum` / `StarRating` /
`RatingDial` / `MetricCard` / `ScrollPicker` / `SwipePager` / `NoteAxisLineChart` / `PhraseTimeline`

## 6. 検証手段（デザイン作業の前提）

### 現状の制約 — 最重要
**このリポジトリでの過去の作業は、すべて数値検証のみで行われた。**
`getBoundingClientRect()` と `getComputedStyle()` で「録音ボタンの下端は590px、ナビは765px」は言えるが、
**「美しいか」は一度も判断されていない。** 目隠しで絵を描いている状態だった。

### 手段
1. **Browserペイン表示 → スクリーンショット**（本人が選択した手段）
   - 現状 `computer{action:"screenshot"}` は失敗する:
     `"the Browser pane is not displayed, so the page is not compositing frames"`
   - **アプリ内でBrowserペインを画面に表示している間だけ**撮影できる。
   - **新セッション冒頭で必ず疎通確認すること。** 通らなければデザイン判断は不可能。
2. **iPhone実機スクショ**（本人から送ってもらう）
   - PWA全画面時の見え方は再現不可能なので、要所でこれが唯一の正解。
3. **HTMLモックアップ → Artifact公開**
   - アプリを描画する必要がないため**上記が全滅でも機能する**。
   - デザイン探索フェーズはこれで完全に進められる。

## 7. 禁止事項・注意

- **470箇所の色を一括置換しない。** 画面ごとに、その画面で使う分だけトークン化する。
  過去に一括置換を「検証できないリスク」として明示的に見送った経緯がある。
- **`pitchBarColorRGB` の緑/橙/赤は機能的意味を持つ**（音程の正誤）。装飾都合で変えない。
- **計測の正確さを装飾で犠牲にしない。** これは計測器であることが土台。
- 変更後は必ず `npx vite build` と `node scripts/pitch-test.mjs`（3811 PASS）を通す。
- iPhone Safari / PWA が本番環境。デスクトップ幅だけで判断しない（375x812 で確認）。
