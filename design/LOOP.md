# 実装ループの運用契約

**目標**: `design/DESIGN-SYSTEM.md` に書かれた状態をアプリ全体で達成する。
達成の定義は `design/BACKLOG.md` の全項目が完了条件を満たすこと。

品質水準は **AAA**（デザイン性・機能性・UI のすべて）。「動いた」で終わらせない。

---

## 1周の流れ（2026-08-04 改訂: 実態に合わせてデプロイと実機確認を正式に組み込んだ）

```
本人の修正依頼 / BACKLOG の次項目
   ↓
① 仕様凍結【統括】
   該当コードを行番号まで特定してから仕様を固める。
   意味が曖昧なとき（例:「安定度」が指す量）だけ本人に質問する
   ↓
①' 波及の洗い出し【統括】★2026/08/25 本人指示で常設
   **本人の修正指示を受けたら毎回、その修正を踏まえて「他に直すべき箇所」を洗い出して提案する。**
   本人の言葉: 「これ以降の修正指示がいたらこれを毎回実施してください」
   見るところ（毎回この順で当たる）:
     1. **同じ部品の他の呼び手** — grep で呼び手を全部数える。片方だけ直すと文法が割れる
     2. **読み手ゼロになる定義** — prop・定数・関数。残すと「使われていない規則」が増える
     3. **同じ裁定で解ける、止まっている起票** — BACKLOG の「本人の判断待ち」を毎回見直す
     4. **共通クラス・共通トークンへの波及** — index.css の作法、DESIGN-SYSTEM の明文
     5. **綴りで縛っている検査** — pitch-test.mjs のどの検査が意味を失うか
   **画面の名前は具体的に書く。**「他3画面」ではなく
   「セッション詳細(SessionDetailView) / リード個体詳細(ReedEvaluationDetail) /
    リード比較(ReedCompareTab)」と、画面名と実装名の両方を出す（本人指示）
   ↓
② 実装【実装役 or 統括】
   大きいバッチ → 実装役エージェントへ委任（下の「実装役の契約」）
   小さい修正 → 統括が直接
   ↓
③ 検証ゲート（4つ全部必須）【統括が独立に実施。実装役の自己申告は採用しない】
   1. npx vite build
   2. node scripts/pitch-test.mjs — 不変条件は FAIL 0（PASS数はガード追加で毎周増える。
      直前コミットの PASS 数を下回らないこと）
   3. Browser pane 375×812 での実測 — ただし下の「Chrome で判定できない類」は除く
   4. 審査役エージェントの辛口レビュー（別 individual。合格/不合格を明言させる）
   ↓
④ 記録【統括】
   BACKLOG.md: F-番号で完了記録+罠を書き、項目を完了記録セクションへ移す
   DESIGN-SYSTEM.md: 規範化すべき作法を追記（**実機で確認できた範囲だけ。仮説を断定形で書かない**）
   pitch-test.mjs: 再発防止の検査を追加（変異試験で「壊すと落ちる」ことを確認してから）
   ↓
⑤ デプロイ【統括】
   commit → featureブランチへ push → main へ fast-forward push → Vercel が自動デプロイ
   本番: https://wind-tone-lab.vercel.app
   ↓
⑥ 本人の実機確認（iOS Safari / PWA）
   ★ Chrome で判定できない類のバグは、これが唯一にして最終のゲート
```

### Chrome で判定できない類（ゲート③の構造的な穴）

**iOS Safari でしか再現しないものは、Browser pane の実測が必ず「合格」を返す。**
その数値を根拠に合格判定してはいけない（date input の幅で3周外した。BACKLOG F-39/F-41）。

該当する既知の領域:
- ネイティブフォームコントロールの固有寸法（`input[type=date]` / `datetime-local` / `select` の幅・高さ・内部テキストの縦位置、`appearance` の有無で挙動が変わるもの）
- セーフエリア（`env(safe-area-inset-*)`）とアドレスバーを含む実機のビューポート挙動
- 実機のタッチ・スクロール・スワイプの体感（Browser pane ではポインタ合成でしか代替できない）

この類を触ったときは、報告に **「Chrome では判定不能・実機待ち」と明記**して⑤まで進め、
⑥の本人確認を完了条件にする。推測で2周続けて外したら、修正を重ねる前に
**再現環境そのものを疑い、本人に端末情報・スクショを頼む**こと。

## 実装役の契約

### 必ず読むもの（この順に）
1. `design/DESIGN-SYSTEM.md` — **値の唯一の答え**
2. `design/BACKLOG.md` — 担当項目の「現状 / 問題 / 方向性 / 完了条件」+ 完了記録の関連する罠
3. `design/DESIGN.md` — 方向性の根拠（育てる × 静けさ / 二面サーフェス）

### 絶対規則
- **`DESIGN-SYSTEM.md` に無い値を発明しない。** 必要なら実装を止めて報告する
- **凍結された仕様が過去の実機報告・コミットの教訓と矛盾していたら、実装せず止めて報告する。**
  統括の指示であっても鵜呑みにしない（F-38 で実装役がこれをやって統括の仕様ミスを止めた。模範）
- **1周で担当項目以外に手を出さない。** 差分が検証不能になる
- **計測アルゴリズム・精度に関わるロジックを触らない**
- **`pitchBarColorRGB` の緑/橙/赤の意味を変えない**
- **色の一括置換をしない。** 担当画面で使う分だけ
- 既存の挙動を巻き添えにしない

### 完了前に必ず通すもの
```bash
npx vite build
node scripts/pitch-test.mjs   # FAIL 0 が不変条件。PASS数は着手前の基準値を下回らないこと
```

### 実測検証（必須。目視の主観で終わらせない）
本番環境は **iPhone Safari / PWA, 375x812**。デスクトップ幅で判断しない。
Browserペインが使えるなら `getBoundingClientRect()` / `getComputedStyle()` で
担当項目の「完了条件」を**数値で**確かめる。確かめられない場合はその旨を明記する。
**「Chrome で判定できない類」（上記）に触れたときは、実測値を合格の根拠にせず「実機待ち」と書く。**

セーフエリアのある実機（`env(safe-area-inset-bottom)=34px`）を想定した確認が必要なときは、
`calc(var(--nav-h) + 34px)` の高さを持つ要素を一時的に置いて実測する
（`getComputedStyle().getPropertyValue()` はカスタムプロパティを未解決の文字列で返すため
`parseFloat` では読めない。過去にこれで一度バグを作っている）。

IndexedDB（`windToneLabDB`）へ合成データを注入して検証する場合:
- `sessions` ストアは inline keys（`id`）。`put(store, value)` にキー引数を渡すと `DataError`
- フレームに `t`（経過秒）が無いと `PhraseTimeline` がクラッシュする
- **検証後は注入したデータを個別に削除して片付ける**（`clear()` / `deleteDatabase` は使わない）
- **dev server のポートを確認してから注入する**（複数ワークツリーの server が並走していることがある。
  `fetch('/src/App.jsx')` の中身に自分の変更が含まれるかで確かめる）

### テストが「通る」ことを根拠にしない

**`scripts/pitch-test.mjs` のハーネスは JSX を見ていない。** `extractFunction` /
`extractConst` でソースから関数・定数を取り出して評価する方式なので、
**描画側（JSX）を壊してもテストは緑のまま通る。**

したがって:
- テストが緑でも「守られている」と書かない。**何がテストで守られ、何が守られていないか**を報告に分ける
- 検査を書いたら、**対象を悪い値に書き換えると実際に落ちること**（変異試験）まで確認する。
  落ちないテストは何も守っていない。変異は実ツリーではなく複製で試し、必ず元に戻す
- **「綴りが無いこと」を主張する検査は `codeOf()`（コメント除去）を通してから見る。**
  通さないと、経緯をコメントに書き残しただけで落ちる（審査役が変異試験で実証済み）

### 過去に2回踏んだ罠: 構造上失敗し得ないアサーション

1回目: `check("重ならない", BEAT_L >= RING_SWEEP_DEG)` — 両辺とも110で**等号でしか通らない**
2回目: 距離から逆算した定数を使い `距離 − (r + halo) > 0` を主張 — 展開すると恒等的に `2 > 0`

**要件は文書に、調整値はコードに、検証はテストに**置き、テストが両者を
**独立に**突き合わせる形にすること。定数の定義を言い換えるテストは書かない。

### 変えたなら「変えた」と数値で書く

**「見た目そのまま」「挙動不変」は、実測して裏を取れたときだけ書く。**
副作用として入った変更も、担当項目に無い変更を入れたなら**報告に1行書く**。書けば通る。黙ると信用が落ちる。

### 報告様式
```
【変更ファイル】一覧のみ
【施工内容】要約。コード全文は貼らない
【検収結果】build / pitch-test / 実測値（完了条件との対応を明示。実機待ちの項目はその旨）
【DESIGN-SYSTEM から引いた値】使ったトークンと値
【担当項目外に入った変更】無ければ「なし」。あれば HEAD との数値比較で
【懸念】無ければ「なし」
```

## 審査役の契約

### 立場
**辛口。** 通すことが仕事ではなく、**欠陥を見つけることが仕事**。
「概ね良い」「軽微な問題はあるが許容範囲」という評価は禁止。合格か不合格かをはっきり出す。

実装役・統括の報告を**信用しない**。報告に書かれた数値は自分で確かめ直す。
「検証した」と書いてあるだけで検証済みと見なさない。

### 必ず読むもの
1. `design/DESIGN-SYSTEM.md`
2. `design/BACKLOG.md` の該当項目
3. `design/DESIGN.md`
4. 実際の差分（`git diff`）と、変更されたコードそのもの

### 審査の観点（すべて確認する）
1. **完了条件を満たしているか** — 数値で確認する。曖昧なら不合格
2. **DESIGN-SYSTEM 準拠** — 勝手な値が入っていないか。トークン外の数値を探す
3. **AAA品質か** — 仕様は満たすが不格好、という状態を見逃さない
   - 375x812 で窮屈・見切れ・重なりが無いか
   - タップ領域44pt以上か
   - 情報の階層が視覚的に表現されているか
   - 二面サーフェスの設計言語が混ざっていないか
4. **余計な手が入っていないか** — 担当項目外の変更、リファクタリング、勝手な機能追加
5. **既存の挙動を壊していないか** — 特に他の画面・他の状態（録音中／メトロノーム開閉等）
6. **コメントと実装が一致しているか** — 陳腐化したコメントは F-37 と同種の負債として指摘する
7. **新設された検査は本物か** — 特に「無いこと」を主張する検査を変異試験で疑う
8. **技術的な妥当性そのもの** — Web上の一次情報と突き合わせる。統括の原因分析が
   間違っていると思えば、遠慮なく不合格にして代案と根拠（出典）を書く

### 報告様式
```
【判定】合格 / 不合格
【不合格の理由】番号付き。各項目に file:line と、なぜ駄目かを具体的に。
                「〜かもしれない」は書かない。確認した事実だけ
【確認した数値】自分で測った値
【見逃していた良い点】あれば1〜2点（無ければ書かない）
```

不合格時は**不合格箇所だけ**を書く。仕様の再説明はしない。

## 進行順

本人の実機フィードバック（F-番号）を最優先。それが無いときは
`BACKLOG.md` の P0 → P1 → P2 → P3 → C の順。

**同じ画面・同じ根本原因の項目は束ねて1周にしてよい**。
束ねた場合は、その理由と束ねた項目IDを報告に明記する。

## 記録

1周終わるごとに:
1. `BACKLOG.md` の該当項目を `[x]` にし、**末尾の「完了記録（罠と経緯の日誌）」セクションへ移す**
2. 実施順を変えた場合・実装中に見つけた罠は項目の下に追記する（失敗と回り道こそ書き残す）
3. 実装中に見つけたスコープ外の問題は、新しい F-番号 / 項目として `[ ]` で起票する
4. 規範化は `DESIGN-SYSTEM.md` へ。**実機で確認できた事実と、未検証の仮説を書き分ける**
   （仮説を断定形で規範化して外した前科がある。F-39）
