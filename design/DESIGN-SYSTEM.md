## 0. 設計の前提

このシステムは**新しい見た目を作るためのものではない**。既に最も多く使われている値を正とし、
判別できない差異を消して、実装が毎回発明していた値を段階に畳むためのもの。

したがって各トークンの値は「今いちばん多く使われている実測値」を採用している。
移行しても**見た目はほとんど変わらない**。変わるのは、次に誰かが書くときに迷わなくなること。

### 1.2 面

| トークン | 値 | 用途 |
|---|---|---|
| `--c-bg` | `#FFFFFF` | ページ背景。**地は白** |
| `--c-surface` | `#FFFFFF` | 面。沈めた面の上に置く白い要素（タイル等） |
| `--c-sunk` | `#F6F7F9` | 沈めた面。**データタブのパネル**（群の境界） |
| `--c-sunken` | `#EEF1F4` | もう1段沈めた面。**B型＝枠線を持たない操作対象の地**（§6.7）・サブタブの溝 |

> **2段ある理由。** `--c-sunk` は「群の境界」（見分けられれば足りる）、`--c-sunken` は
> 「ここは触れる」（操作できると分からせる）。後者のほうが強い信号が要る。
> 白地との差は **1.0719:1 / ΔL\* 2.79** と **1.1337:1 / ΔL\* 5.00**。

> **地が白なので、カードは「地より明るい面」では区別できない。** まとめ方は §6.6 の
> 「面の作法」が**画面ごと**に決める（D-10 でタブ単位から画面単位へ細かくなった）。
> My Data と分析タブだけは地を `--c-sunk` へ下げ、その上に白いカードを浮かせる。`--c-surface` は地と同値だが、**沈めた面の上に置く白**
> という別の役割で残している（値が同じでも役割が違うトークンは分ける。`--c-on-accent` と同じ考え）。

> `--c-sunk` は旧来の地の値をそのまま流用している。白地との差は **1.0719:1 / ΔL\* 2.79**。
> これは旧来の「白カード vs 地 `#F6F7F9`」とまったく同じ差で、**データタブの群の境界は
> 旧来と同じ強さ**。一度 `#F7F9FB`（2.17）にして弱めたことがあるので、
> `scripts/pitch-test.mjs` が **1.0719:1 を下限として**縛っている。**値ではなく差で縛る。**

| 用途 | 太さ |
|---|---|

### 1.9 グラフの寸法要件

グラフは**コンテナ実測値に追従**させる。固定幅にしない。

| 要件 | 値 |
|---|---|
| SVG の実寸 : `viewBox` 幅 | **1 : 1**（`preserveAspectRatio` による全体縮小は禁止） |
| 項目ラベル欄の上限 | コンテナ幅の **42%** |
| 目盛ラベルの左右余白 | **`--sp-2`（8px）以上** |
| 目盛ラベルの上下余白 | **`--sp-1`（4px）以上**（ディセンダと書体差の逃げ） |

> **縮小禁止の理由**: 全体を縮めれば固定幅でも収まるが、12px の文字が実効 9.6px になり
> §4.1 のサイズスケールが無意味になる。文字は常に真のpxサイズで描く。

> **余白が `--sp-2` の理由**: `getComputedTextLength()`（送り幅）と実際のインク幅は一致せず、
> 和文グリフはインクが送り幅を **最大1.6px程度**超える（実測値）。この超過量は書体とグリフ次第で
> 上限が保証されないため、`--sp-1`(4px) では「検証したら足りていた」に留まる。
> 余白は `--sp-2`(8px) を取るか、`getBoundingClientRect()` の実インク幅で検算して決める。

> SVG のプレゼンテーション属性には `var()` が書けない。数値を使う場合は
> ファイル内に1つ定数を置いてそこから引き、マジックナンバーを散らさないこと。
> 色は `style` 属性なら `var()` が解決される。

### 1.11 動きの時間と曲線（2026/08/27 本人指示・D-11 §1）

**これまで体系に「動き」の節が無かった。** 時間と曲線が App.jsx と index.css に散らばっていて、
どれが規範でどれが場当たりか読めなかった。ここが**開閉の動きの唯一の答え**。

本人の言葉:「日付を押したときの開き方が全くスムーズではないのでもっと**ぬるっと**動くように」。

| 動き | 時間 | 曲線 | 遅延 | 持ち主（CSS） |
|---|---|---|---|---|
| 枠を開く（高さ） | `320ms` | `cubic-bezier(0.32, 0.72, 0, 1)` | `0ms` | `.day-panel.is-open` |
| 枠を閉じる（高さ） | `240ms` | `cubic-bezier(0.32, 0.72, 0, 1)` | `0ms` | `.day-panel` |
| 中身が現れる（opacity / transform） | `220ms` | `cubic-bezier(0.32, 0.72, 0, 1)` | `60ms` | `.day-panel.is-open .day-panel-inner` |
| 中身が消える（opacity / transform） | `140ms` | `cubic-bezier(0.32, 0.72, 0, 1)` | `0ms` | `.day-panel-inner` |

**この表の値は `scripts/pitch-test.mjs`（検証33）がこのファイルから読んで
`src/index.css` と突き合わせる。** 数値をテストに直書きしていないので、
値を変えるときは**この表を直せば検査もそれに追随する**（表と実装が食い違ったら落ちる）。

#### 作法（ここから外れるものを足さない）

1. **開閉は非対称にする。** 開くほうを長く、閉じるほうを短く。
   閉じる動きは「もう見終わったもの」なので待たせない。
   **範囲（2026/08/27 追記）: これは `.day-panel`（日付を押して開く枠）1つで採った値であって、
   体系の作法として検証してはいない。** 非対称にしたこと自体も 320/240 という比も、
   本人の実機で「ぬるっと」の判定を受けていない（下の「実機待ち」）。
   他の開閉（シート・アコーディオン・ダイアログ）へ広げるときは、
   **その部品で採り直す**こと。1つの部品・実機未確認から体系の作法を断定して外した前科がある
   （F-39。この規範文書は同じ型の失敗を通算3回している）
2. **時間・曲線・遅延はインライン style に書かない。** CSS のクラスが持つ。
   そうしないと `prefers-reduced-motion: reduce` を1箇所で尊重できない
3. **中身も動かす。** 器の高さだけを動かすと「箱がマスクで刈り取っている」ように見え、
   それが「硬い」の正体だった。中身は器より**遅れて現れ、先に消える**
4. **中身の閉じ側の初期姿勢は `translateY(-8px)`。** 開くとこれが `none` へ戻る
5. `prefers-reduced-motion: reduce` では **上の4行すべてを止め、
   中身を `opacity: 1` / `transform: none` へ戻す**。止めるだけだと
   「中身が透明のまま残る」事故になる

#### 実測できた事実（Chrome 375×812・dev server）

- `.day-panel` の computed `transition` は 閉 `height 0.24s cubic-bezier(0.32, 0.72, 0, 1)` /
  開 `height 0.32s cubic-bezier(0.32, 0.72, 0, 1)`
- `.day-panel-inner` の computed `transition` は 閉 `opacity 0.14s …, transform 0.14s …`（遅延 0s）/
  開 `opacity 0.22s … 0.06s, transform 0.22s … 0.06s`
- 閉じているときの `.day-panel-inner` は `opacity: 0` / `transform: matrix(1, 0, 0, 1, 0, -8)`
- 枠を開くと「すべてのセッション」の `top` が 548.6 → 752.6 = 枠の高さ 204px ぶん動き、
  閉じると 548.6 へ戻る（下のカードの押し出しは壊れていない）

#### `will-change` は付けない / `contain` も入れなかった（2026/08/27）

D-11 の凍結仕様は `.day-panel` に `will-change: height` と `contain: layout paint` を
足すよう指示していたが、**どちらも当てていない**。ただし
**2つの理由はまったく別物**で、一方だけが規範による禁止である。

##### (a) `will-change` — アプリ全体で禁止（規範。ここは初版のまま正しい）

`scripts/pitch-test.mjs:16214`
「30.1 F-106: アプリ全体で will-change を1つも使っていない」が固定している。
F-106 は**実機でしか出なかったバグ**で、恒久的なレイヤ昇格を外して直したもの。
`.day-panel` の中には `overflowY: auto` + `WebkitOverflowScrolling: "touch"` の
スクロールコンテナがある（`src/App.jsx:12416`）。

##### (b) `contain` — **方針としては禁止されていない**（2026/08/27 訂正）

**この節の初版は「`contain` / `content-visibility` / `transform` も F106-SPEC が名指しし、
`30.1 F-106` がこれを固定している。実際に当てたらこの検査が落ちた」と書いていた。
これは事実と違う。** コードで確かめた結果:

- `contain` / `content-visibility` / `transform` を見ている検査は
  `scripts/pitch-test.mjs:16206` の**1つだけ**。その走査対象 `listCss`（`:16202`）は
  `/(\.slist[\w.-]*(?:\s+\.[\w-]+)?)\s*\{([^}]*)\}/g` ── **`.slist*` セレクタだけ**で、
  `.day-panel` も `.day-panel-inner` も対象外
- `design/F106-SPEC.md:23` の原文も
  「**一覧の行やスクロールコンテナに**使っている箇所があれば外す」であって、アプリ全体の禁止ではない
- **実測**（この worktree の複製ツリー・`node scripts/pitch-test.mjs`。基準は PASS 6742 / FAIL 0）:

  | `.day-panel` に足したもの | FAIL | 落ちた検査 |
  |---|---|---|
  | 何も足さない（基準） | 0 | ── |
  | `will-change: height` | 2 | `D-10 §4: 開閉の動きは .day-panel が持つ` ＋ `30.1 F-106`（app-wide） |
  | `contain: layout paint` | **1** | `D-10 §4` **のみ**（F-106 は1件も落ちない） |
  | `position: relative`（まったく無害な1宣言） | **1** | `D-10 §4` **のみ** |

  その1件は `scripts/pitch-test.mjs:5933` の
  `/\.day-panel\s*\{\s*transition:\s*height\s+([^;]+);\s*\}/` ──
  **`.day-panel { }` の中身が `transition:` 1宣言ちょうどでないと外れる**正規表現で、
  主張しているのは「時間と曲線の**置き場所**」であって F-106 の方針ではない。
  無害な `position: relative` でも同じ1件が落ちる（起票済み: BACKLOG「D-12c」）

**`contain` を入れなかった理由**（成立するのはこの2つだけ）:

1. `contain: layout` が切るのは要素の**内部**レイアウトの独立性であって、
   要素自身の使用高さが親のフローに与える影響は切らない。凍結仕様が挙げた
   「下の折れ線 SVG が毎フレーム再レイアウトされるのを抑える」は達成できない
   ── ここで毎フレーム外を動かしているのは**枠の高さそのもの**（＝下のカードを
   押し出すという意図した挙動）で、これが切れたらむしろ壊れる。
   `contain: paint` の効果は既にある `overflow: hidden` と重複する
2. `contain: layout` / `paint` は **`position: absolute` / `fixed` の子孫に対する
   新しい包含ブロックと、新しい stacking context** を作る
   （MDN `contain`: "Using `layout`, `paint`, `strict` or `content` values for this
   property creates: 1. A new containing block … 2. A new stacking context.
   3. A new block formatting context."）。この枠の中には `PlainSelect` の
   `position: absolute` があり、アプリは fixed の portal（浮かせるボタン）も使うので
   巻き込む余地がある

Chrome では `contain: layout paint` を当てても描画は壊れなかった（押し出し 204px を実測）が、

### 4.2 演奏中サーフェス専用スケール（音名の組み方）

7段とは別系統。**確定済み（2026-07-31）。**

| 定数 | 値 | 対象 |
|---|---|---|
| `NOTE_FS_RATIO` | **`0.3576`** | 音名の文字サイズ = **環の直径 × この比** |
| `NOTE_SCALE_X` | **`1.30`** | 音名の横幅。`transform: scaleX()` で明示指定 |
| `NOTE_ACC_RATIO` | `0.34` | 臨時記号 ♯/♭ = 音名サイズ × 0.34 |
| `NOTE_OCT_RATIO` | `0.31` | オクターブ数字 = 音名サイズ × 0.31 |

**音名は環の直径に比例させる（固定pxにしない）。**
環が縮んだときに音名だけ据え置くと、音名と環内周の余白（クリアランス）が
55px/辺 → 14px/辺 のように4倍近く変わり、同一サーフェス内で見え方が別物になる。
比で持てば、環がどの大きさでもクリアランスの比率が一定に保たれる。

| 環の直径 | 音名サイズ | 使う場面 |
|---|---|---|
| `RING_D_FULL` = `330px` | 118px | **常にこれ**（素のチューナー / メトロノームを開いている間とも） |

> **環はメトロノームの開閉で大きさを変えない（2026-07-31 確定）。** 以前は開くと 330→250 に
> 縮めていたが、演奏中サーフェスの主役が開閉のたびに別の大きさになるのは読み取りを妨げる。
> 縮小で捻出していた縦スペースは、**メトロノームを開いている間だけ「これまでの音」
> （`PitchDeviationLine`・quiet時94px）を隠す**ことで確保する。メトロノーム使用中は
> リズムに集中していて、ピッチの履歴は合間に読むものだから。
> 比の仕組み（`NOTE_FS_RATIO × 環の直径`）は残す。環が固定なので結果は118px固定になる。

**クリアランス要件**: 最も幅の広い音名（`G♯3` 等、臨時記号＋オクターブ付き）でも、
`scaleX` 適用後の視覚幅の左右端が環の内周に対し **音名サイズの10%以上**の余白を持つこと。
実測で確認する。

**横幅を明示する理由**: Instrument Serif の既定の送り幅は **0.457em**（一般的なserifの64%）。
細さ自体は1m先から読む演奏中サーフェスに合っているが、書体既定のままでは
「幅を選んでいない」見え方になる。`scaleX(1.30)` を掛けて **0.594em** にする。

**scaleX のレイアウト補正**: `transform` は要素のレイアウト幅を変えないため、変形後のグリフが
左右に `(1.30-1)/2 = 15%` はみ出す。送り幅 0.457em の15%分を左右marginで補う
（`NOTE_SCALE_PAD_EM`）。これを入れないと臨時記号と重なる。

**臨時記号の扱い（確定）**
- **文字として組む**（SVGで描かない）
- **`scaleX` は掛けない**。本体だけに掛ける
- 音名本体と近いサイズにしない。**付属物として明確に小さく**する
- 既知の制約: `♯`(U+266F) `♭`(U+266D) は Instrument Serif に**収録されていない**ため
  フォールバック書体で描画される。この見え方を採用する判断済み

#### 軸の行の例外は無くなった（2026/08/26・D-10c 本人裁定）

軸の行（`縦軸 / 横軸 / 分析軸`）は D-10 で 30px の例外だったが、**44pt へ戻した**。
本人の裁定:

> ラベルを値の上に積む

つまり `縦軸 音名 ▾` と1行に並べる形（`inline`）をやめ、**ラベルが上・値が下**の縦積みに戻す。
狙いは、値に列の幅をまるごと使わせて**長い選択肢を見分けられるようにする**こと。
行は 30 → 44px（**+14px**。変更後の操作カードは **106px 実測**で、変更前は 30+30+`--sp-4` 16×2 = **92px**）だが、
**そのかわり 44pt に満たない例外が1つ減る**（§5 の例外は「式の行」と「条件チップの行」の2つ）。

**器は3カラムの等幅グリッド**（`display: grid` / `grid-template-columns: 1fr 1fr 1fr` /
`gap: var(--sp-2)` = 8px / 各セル `min-width: 0`）。列の境界に罫は引かない。
実測（375×812・Browser pane）: 列は **99.66 / 99.67 / 99.66 × 44**、行は 315px で
`scrollWidth − clientWidth = 0`。

**なぜ「等幅」なのか ─ 下限（`min-width`）で解こうとして失敗した記録**

D-10b は `min-width: 87px` の下限を1アイテムずつに置いた。**これは間違いだった。**

- **CSS の `min-width` は無条件の床**である。「行が溢れそうなときだけ効く」ものではなく、
  **自然幅が 87px に満たないアイテムを 87px まで押し広げる**。
  その結果、幅が余っていた組にまで不足を作った。
- 審査役の A/B 実測（同一ページ・同一データ・`min-width: 0 !important` を注入して比較）:
  既定の組（音名 / 平均差分(¢) / リード銘柄）は**下限なしなら3つとも全部出る**
  （63.77 / 112.45 / 118.78）のに、**下限ありでは2つが切れた**
  （87.00 / 105.84 / 102.16。縦軸は 23.23px の空白を抱えていた）。
  30組の走査で、1文字も切れない組は **18/30 → 4/30**（**14組が悪化**）。
- 等幅グリッドなら列の幅は綴りに依存しないので、**取り合いそのものが起きない**。

**同じ型の誤りを次に持ち込まないために**（この節は同じ失敗を2回している）:
「flex の縮み順」も「下限」も、**行の中で幅を配分する規則**であって、
「どの綴りが何文字読めるか」を決められない。読めるかどうかは**実測でしか出ない**。
この節に一般化を書くときは、**測った範囲を必ず添える**こと。

**実測（375×812・Browser pane。`getComputedStyle` のフォントを canvas `measureText` に写し、

### 6.1.5 レイアウトの安定（全画面に適用する規則）

> **何かを開いても、閉じても、値が変わっても、既にあった要素は1pxも動かない。**

本人の指摘（2026-08-01）:
> メトロノームにすると円やボタンなどの上下位置がズレる
> メトロノームなしの時の詳細を表示するとメータの上下位置がブレる
> **とにかくどのページでも追加表示で元のある表示がぶれないようにして**

**原因になる書き方（禁止）**

| 禁止 | なぜ |
|---|---|
| 高さが変わるコンテナに `justify-content: center` | 中身が増減するたび**既存要素が動く** |
| 状態で `justify-content` を切り替える | 切り替えた瞬間に全部動く |
| 出現・消滅する要素の**場所を確保しない** | 出た瞬間に下が押し下げられる |

**正しい構造**

```
[ 上端に固定 ]  設定行など、常にあるもの
[ 固定の間隔 ]  --sp スケールの固定値。状態で変えない
[ 主役 ]        環・メーターなど。★ここは絶対に動かさない
[ 可変の中間 ]  flex:1。状態ごとに中身が入れ替わる（履歴グラフ / 操作UI / 空）
[ 下端に固定 ]  録音ボタンなど、常にあるアクション
[ 追加表示 ]    詳細カードなど。ここから下だけがスクロールする
```

**主役は上から固定の距離**に置き、**アクションは下端に固定**する。
増減するものは**その間**に入れ、余りは中間が吸収する。こうすると
「何を開いても主役とアクションは動かない」が構造で保証される。

**値の出し入れも同じ**: 音が入っていないときに文字を消す場合も、
**領域は確保したまま文字だけ消す**（`—` を出す必要はないが、箱は残す）。
文字の有無で高さが変われば、それも「ぶれ」になる。

**検証**: 状態を切り替えて、主役とアクションの `getBoundingClientRect().top` が
**1px も変わらない**ことを実測する。目視で判断しない。

#### 過渡的な告知は「流れから外す」

録音中・解析中・確認ダイアログのような**過渡的な告知**は、`position: fixed` で
**レイアウトの流れから外す**。流れの中に置くと、上端に置けば主役が動き、
中間に置けば余りを食い潰してアクションが動く（どちらも実測で確認済み）。

**座標はルートの `padding` と同じ式を使う**。
```
top:   calc(16px + env(safe-area-inset-top))
left:  calc(14px + env(safe-area-inset-left))
right: calc(14px + env(safe-area-inset-right))
```
別管理にすると、セーフエリアのある端末でコンテンツ列とずれる。

**容器は `pointer-events: none`、カードだけ `auto`。**
全幅の透明な層を敷くと、告知が出ていない領域まで下の操作を殺す。

> **計測タブでモーダルを垂直中央に置くことはできない。**
> 環は `top 147 / bottom 477`、ビューポート中央は `812/2 = 406` で、
> **環が中心点を跨いでいる**。中央に置いた要素は高さが何pxでも必ず中心点を含むため、
> **カードを小さくしても環と重なる**。下寄せにすること
> （下余白は `calc(var(--page-bottom-gap) + var(--sp-4))`）。

**「押しても何も起きない」を作らない。**
告知が下の操作を覆う場合、覆われた側は**無反応ではなく `disabled` にする**。
無反応は「アプリが固まった」と解釈される最悪のフィードバック。

### 6.3 横スワイプの作法

**この作法はアプリ内で1つだけ**。「指に追従する」以外の横スワイプを作らない。閾値だけを見て指を離すまで何も動かないスワイプは、動いていないのか効いていないのか奏者に区別がつかない。

| 定数 | 値 | 意味 |
|---|---|---|
| しきい値 | 動かす面の幅の **20%**（幅が測れなければ 60px） | 「動かす面」は viewport の `clientWidth`。画面幅ではない。375px 端末の詳細画面では 347 × 0.2 = **69.4px** |
| 軸ロック距離 | **6px** | 縦横どちらのジェスチャーかを決め始める移動量 |
| `SWIPE_VERTICAL_BIAS` | **1.5** | **縦と断定するには縦成分が横成分の 1.5 倍以上必要**。境界は `atan(1.5) = 56.31°` |
| 行き先の無い向きの抵抗 | **0.35** | 動くが遷移しない |
| 戻すときの動き | `transform 0.32s cubic-bezier(.22,.61,.36,1)` / 後始末は **320ms** | この2つは必ず同じ値。片方だけ変えない |

#### 軸を「勝つまで決めない」

横確定 = `|dx| >= 6 && |dx| > |dy|` ／ 縦確定 = `|dy| >= 6 && |dy| >= |dx| * 1.5` ／ **それ以外は未確定のまま観察を続ける**。

親指のスワイプは根元を支点に弧を描くので、最初の6pxは縦成分が勝ちがちで、**画面下ほど弧が急になる**。一度きりの `|dx| > |dy|` で決めると、横スワイプが一度の揺れで縦に固定される。CDP 実測で、この規則の導入前は**水平0°の純粋な横ドラッグですら20本中1本も通らなかった**（20px 進んだ時点で `pointercancel`）。導入後は 20/20。

1.5 が実際に救うのは **42〜44° の帯**（丸めのゆらぎで一瞬 `|dy| >= |dx|` になるところを断定せずに拾い直す）。46〜70° の弧は 1.0 でも 1.5 でも成立しない。45〜56.31° の直線ドラッグは未確定のまま終わる（この設計の帰結。BACKLOG F-20）。

#### ブラウザにスクロールを横取りさせない

**非パッシブの `touchmove` を張り、横と確定している間だけ `preventDefault()` を呼ぶ。** Pointer Events だけではブラウザのスクロール開始を止められず、斜めに引くと `pointercancel` が飛んでジェスチャーごと死ぬ。

**`touch-action` は使わない。** 祖先の指定が子孫より優先されるため、`pan-y` を敷くと中にある横スクロール表が動かせなくなる。

**未確定のうちは `preventDefault` してはいけない。** iOS は最初の `touchmove` で `preventDefault` されるとそのジェスチャー全体をスクロールしなくなるので、縦スクロールが死ぬ。

#### 動かす面の構造

`overflow: hidden` の viewport が track を包み、**動かすのは track だけ**。包まないとドラッグ量ぶんページが横に伸び、ページ全体が横スクロールできてしまう（実測 `scrollWidth 375 → 422`）。

**静止時に `transform` を残さない。** identity（`translateX(0px)`）でも、`transform` がある要素は `position: fixed` の子孫の包含ブロックになり、モーダルの暗幕が画面全体を覆えなくなる。同じ理由で **`will-change: transform` も使わない**。

**ジェスチャーの終わり方は3つ**: `up`（行き先判定あり）／`cancel`（戻すだけ）／**別の `down` による中断**。中断の終端は**対象判定より前**に置く。「対象外かどうか」は新しく始めるかの判断であって、前のを終わらせるかの判断ではない。これを取り違えると、2本目の指が触れた瞬間に進行中のドラッグが後始末なしに捨てられ、**画面がずれたまま無期限に固着する**（実測で最大200px）。

| 項目 | 範囲 | 刻み | 表示 |
|---|---|---|---|
| 総評 | 1.0〜5.0（41段） | **0.1** | 常に小数第1位（`3.7` / `3.0`） |
| 厚さ | 1〜5 | 1 | 整数 |
| バランス | 1〜5 | 1 | 整数 |

- **比較する前に必ず丸める。** 0.1 刻みは2進小数で正確に表せないので、生の `===` で「変更あり」を判定すると**開いただけで記録される**。丸めは「刻みに乗せる」→「小数第1位に落とす」の二段（`Math.round(n/0.1)*0.1` → `Math.round(r*10)/10`）。二段目は必須（外すとダイヤル41段のうち15点が `1.2000000000000002` のような値で保存され、位置が引けなくなる）。
- 評価の推移グラフの縦軸は **1〜5 のまま**。総評だけが小数を取る。

### 6.5 チューナーの環の配色と到達

#### 機能色（意味を持つ。装飾都合で変えない）

| セント差 | 色 | |
|---|---|---|
| 0¢ | `#16A34A` | 緑 |
| **8¢** | `#D97706` | 橙。実用域が ±10¢ なので、その中で緑→橙を使い切れる位置に置く |
| 30¢以上 | `#DC2626` | 赤 |

**補間は必ず OKLCH。** sRGB で直線補間すると中間で彩度が落ちて濁る。緑→橙の中間（4¢）で
sRGB は `rgb(120,141,40)` の濁ったカーキ、**OKLCH は `rgb(160,145,0)` の澄んだ金**。
色そのものは1つも変えていないのに見え方が別物になる。**ここが「安っぽい」の主因だった。**

#### 帯（ズレの表示）

| 値 | |
|---|---|
| `RING_RAMP_REF = 62` | 先端から数えて色を作り込む弧長（viewBox単位 ≒ 11.9¢） |
| `RING_RAMP_STOPS = 30` | ストップ数 |
| 明度差 | `0.105e − 0.062(1−e)` |
| 彩度倍率 | `1.12 − 0.30e` |
| 色相ずれ | `−9e + 7(1−e)` 度 |

`e = smoothstep(clamp(s / RING_RAMP_REF, 0, 1))`、`s` は**先端からの弧長**。

- **帯の長さで正規化してはいけない。** ±24¢ の帯は弧長125px、±8¢ は42px。同じ工程を押し込むと
  3分の1に圧縮されて**断層として見える**。実用域は ±10¢ なので、そこで成立しないと意味がない。
- **3要素すべて単調。明るさの山（芯）を置かない。** 単調なら断層は原理的に出ない。
  実画素で確認済み: ±8¢ の帯の隣接画素の最大差 **3/255**、RGB 各成分が単調。
- **不透明度は常に 1。** `stop-opacity` を1つも書かない。根元が透けると下地が出る。
- **ストップ位置は弧を弦へ射影して決める。** グラデーションの軸は弦なので、等間隔に置くと
  色の位置がずれる。検査は「各ストップの点と弦上の offset 位置の差が**弦に垂直**」を内積で見る
  （等間隔を 1% 混ぜただけで落ちる）。
- **`stroke-linecap` は `butt`。** 丸端は終点から `RING_SW/2 = 7` 外へ張り出し、
  (a) 0¢ の基準線を越えてはみ出す (b) 張り出した半円が最終色でベタ塗りされ
  **「別の丸いものが付いている」ように見える**。
- **先端に点を置かない。** 先端はグラデーションの終わりであって、付属物ではない。

#### 到達（±2¢）と、その手前の光（±4¢）　※F-47 で更新

**判定線は `RING_IN_TUNE_CENTS = 2`**（本人指示 2026-08-08。以前は 1）。

| 値 | |
|---|---|
| `RING_IN_TUNE_CENTS = 2` | これ以内なら「合った」。走りが出る |
| `RING_GLOW_NEAR_CENTS = 4` | ここまでは走らせず**光だけ**を出す |
| `RING_RUN_MS = 640` | 12時から6時へ走り切るまで |
| イージング | ease-out cubic `p => 1 − (1−p)³` |
| `RING_BREATH_MS = 2600` | 呼吸の周期 |
| `RING_BREATH_RISE = 0.50` | 周期のうち上りに使う割合 |
| `RING_GLOW_AMP = 0.90` | 光の最大の強さ |
| `RING_RUN_REARM_MS = 1200` | 外れた状態がこれだけ続くまで走り直さない |

**段の切り分け**（`ringGlowOpacity` に閉じ込める。rAF 側に条件分岐を置かない）:

| ズレ | 走り | 光 |
|---|---|---|
| ±2 以内 | 出る | 出る（呼吸つき） |
| ±2〜±4 | **出さない** | 出る。±4 に近づくほど連続的に 0 へ |
| ±4 超 | 出さない | **0** |

- 走りは**左右同時・完全対称**（実測の角度差 5.68e-14）。終端は **±180.0000°**。
- 光は**環の外側だけ**。内側は完全に白のまま。**音名の可読性と静けさのため、これは要件。**
- 光の色は `tune(base, dL +0.16, 彩度 0.62倍)`。**「光源の色」ではなく「照らされた面の色」**にする。
- 呼吸は正弦波ではなく **smoothstep を上り下りに分けたもの**。
- 実効の不透明度 = `AMP × 走りの線形進捗 × (0.34 + 0.66 × 呼吸)`。走りに合わせて光が立ち上がる。
- **減速設定では走らず点灯状態から始め、呼吸も止める。ただし光は消さない。** 到達は伝える。

> **判定線の色はベタ判定しない。** `pitchBarColorRGB` は連続補間なので、±2 ちょうどで閉じる円は
> 色相 76°の黄緑 `rgb(113,156,0)`（0¢ は 142°の緑 `rgb(22,163,74)`）。
> 本人指示は「±2以内で**緑円**判定」だが、閾値で色を切り替える実装にはしていない
> （§1.5 の機能色を閾値で階段状にすると意味体系が壊れる）。**「これで緑と感じるか」は実機の判断。**

##### 外周の光の作り方（F-47）

環の縁から間接照明のように漏れる光。**実装の要点は `src/App.jsx` の `ringGlowAlphaAt` 直上の
解説を読むこと。** ここには設計上の約束だけを書く。

- **光の最大は環の外縁に置く。** 立ち上がりを外縁より外まで続けると、環と光の間の数pxが
  淡いまま残り**細い明るい線**が見える（試作で本人が指摘した不具合）。
- **終端で値も傾きも0にする。** `exp(-decay·x)·(1-x)³` は x=1 で値も微分も 0。
  ここが折れると「グラデーションの終わり」が縁として見える。
- **`mix-blend-mode` を使わない。** 試作の初版は粒をマスクの中で `multiply` で重ねており、
  その指定が効かない環境で**画面全体が緑になった**（本人報告）。マスクの入れ子（=掛け算）だけで作る。
  減衰マスクを常に最外に置けば、どんな事情があっても環の外側へ漏れない。
- **毎フレーム変えるのは明るさだけ。** ストップも粒も静的に1度だけ作る。
- 光は viewBox の外まで届くので `overflow:visible` が要る（r=150 で peak の 42.6% が残っており、
  切ると四角い縁が出る）。同時に `pointerEvents:"none"` が**必須**（無いと光の矩形が
  下の操作の当たり判定を奪う）。**この2つは対で、片方だけでは成立しない。**

> **粒（`feTurbulence`）は入っているが、画面には出ていない。** 本人が「粒の表現が要るかも」と
> 要望した経緯で機構は残してあるが、実測では寄与が **0.972/255**（本人選定の試作も 0.983/255 で
> 事実上同じ）。**`RING_GLOW_GRAIN_LO` / `RING_GLOW_RAMP_POW` を動かしても点かない**
> （grainLo 0.30→0.00 で 0.972→0.972）。効かせるには `falloff × ramp` の掛け算の構造を変える必要がある。
> **「外へ行くほど粒に分解して散る」と書かないこと。**

#### 再走行の抑制

判定線の上でピッチが揺れると走りが何度も起きる。**一度走ったら、外れた状態が
`RING_RUN_REARM_MS` 続くまで走り直さない。** 抑制中に戻った場合は走りをやり直さず
点灯状態（進捗1）から始める。

> **1200 の根拠を取り違えないこと。** 実コンポーネントを 60fps で駆動して `inTune` が偽である
> 連続時間を測ると、判定線の上で揺らした場合は **233〜650ms**（3¢/1.5Hz で 233〜267ms、
> 2¢/0.5Hz で 633〜650ms、1.2¢/3Hz では EMA が吸収して一度も外れない）。
> 900ms を超えるのは **+15¢ に約650ms 保持してから戻す**ような場合で、これは「揺れ」ではない。
> 1200 を選んだのは、生の外れが 800ms までは走らず 1000ms 以上で走る（実効しきい値は生で
> 約930ms）という掃引の結果、**「本当に外して戻った」ときは走る**という性質を保てるため。

#### 作法に共通

- **操作するもの（入力欄・ボタン）の見た目は §6.7 が決める。** 面の作法（罫／沈める）は
  「群のまとめ方」だけを決め、操作するものには触らない。**§6.7 を見ること。**

- **個々の要素が `background` / `border` / `borderRadius` / `padding` を
  インラインで書いてはいけない。** インライン style は CSS より強いので、書いた要素だけ
  作法が効かなくなる。これが**この設計でいちばん壊れやすい点**なので、
  `scripts/pitch-test.mjs` が接頭辞で検査している（`backgroundColor` のような
  キャメルケースの別綴りで一度すり抜けた実績がある）。
  **`gap` は `.tile-row` だけが作法の管轄**（罫の作法では 0 にして罫で分ける）。
  `.card` の中身の並びは各画面の裁量なので、`.card` に `gap` を書くのは可。
- **`index.css` の末尾に同じセレクタで上書きを追記してはいけない。** CSS は後勝ちなので
  作法が丸ごと反転する。これも検査で縛っている。

- **特定1〜2箇所だけ作法の一部（例: 上辺の罫）を消したい場合は、`.card` を含む複合セレクタ
  ではなく、`.card` という文字列を一切含まない別名クラスを使うこと。** `.card.foo` のような
  複合セレクタは検査の `targetsClass("card")` 正規表現に「`.card` に触れている」と
  誤検出される。別名クラス（例: `.no-top-rule`）を、上書きしたい規則と**同じ詳細度**で
  その直後に置けば、CSSの宣言単位カスケード（プロパティごとに後勝ち）で狙った1プロパティ
  だけが上書きされ、他は元の作法のまま生きる。乱用しないこと（本人が明示した箇所だけに使う。
  リード登録カード／リード個別詳細の識別情報カードの上辺の罫、2026-08-04）。

### 6.7 枠線は「状態を持つもの」にだけ使う

**同じ物に「枠線」と「違う地の色」を両方与えない。** どちらか一方で足りるものに両方やると重くなる。

| 型 | クラス | 見た目 | 対象 |
|---|---|---|---|
| **A型** | `.ctl-state` | 枠線 `--c-line-strong` / 地は透明。**ON は枠線の色だけ** `--c-accent` に変える | **状態を持つもの**（on/off・開/閉・選択中/非選択） |
| **B型** | `.ctl-plain` | **枠線なし** / 地は `--c-sunken` | **状態を持たないもの**（入力欄・選択欄・普通のボタン） |

> **これは読み手への約束になる。「枠線があるものは状態を持っている」。**
> メトロノームに枠線を残す理由（on/off が分かるべき）が、そのまま全体の規則になった。

| 対象 | 型 |
|---|---|
| メトロノーム / 拍子 / 1拍の分割 / 詳細トグル | **A** |
| 入力欄（`input` / `select` / `textarea`）全般 | **B** |
| リード登録の 銘柄・番手・使用開始日 | **B** |
| データタブの絞り込み・奏者選択・リード選択ピル | **B** |
| 状態を持たないボタン（追加・キャンセル・クリア等） | **B** |

**ON の合図に地を足さないこと。** 枠線の色だけで返す。地を足すと A型が「枠線＋違う地」になり、
規則そのものを破る。

#### 破壊的な一手だけは塗ってよい

**実際に削除が実行されるボタン**は `--c-danger` の塗り + `--c-on-accent` の文字（**4.83:1**）。
枠を持たないので芯に反しない。地を `--c-sunken` にすると文字が **4.26:1** で AA(4.5:1) を
下回るため、この一手だけ「塗りの強調ボタン」と同じ扱いを許す。
**「削除モードに入る入口」は塗らない**（破壊がまだ起きないので中立の `--c-ink-2`）。

#### 意図した例外（潰さないこと。**全部で6グループ**）

1. `select.pivot-axis-select`（データタブの軸選択・3個）— 表の見出しの中なので枠が表の罫と喧嘩する
2. 計測タブのリード選択ピルの中の `<select>` 2個 — ピル自身が地を持つので中は素のまま
3. **START/STOP** — 状態を持つが、ON は `--c-danger` の枠、OFF は `--c-accent` の塗り。
   A型に流すと**意味色が状態色に化けて §1.5 が崩れる**。実測でどちらの分岐でも
   「見える枠」と「違う地」は同時に立たないので**芯には反していない**。
4. **子タブのセグメンテッドコントロール** — 溝の中で選択中だけが白く浮く。
   枠線を持たないので芯には反しないが、状態を**地**で返すので A型ではない。
5. **塗りの強調ボタン**（録音する / まとめて追加 / 登録 / 完了 / 保存 / 追加 / 変更）—
   枠なし・地だけで芯を満たす。地が `--c-sunken` ではなく `--c-accent`。
6. **通知面**（警告・アップロード告知・`ScrollPicker` の選択帯）— 枠と地を両方持つ。
   **群でも操作でもない第3の種別**で、A型/B型のどちらにも属さない（BACKLOG F-33）。
   タップで消せるものは操作にも見えるが、**線は「操作するものか」ではなく
   「情報を伝える面か」で引く**。検査から明示的に除外してあり、黙って外れているのではない。
   **マイク許可エラーはこの群から抜けた**（2026-08-04）。放置せず必ず閉じるべき操作なので、
   `pendingSession` の保存確認と同じ「下寄せの暗幕モーダル」（§6.1.5 の確認ダイアログ）に
   変更した。現時点で `data-frame-exempt` は **0件**（この群自体は将来の警告UIのために残す）。

> **例外は必ずここに書くこと。** 検査が 0 FAIL を返すだけでは、次の実装役に
> 「例外なのか未対応なのか」を判別する手段がない。

#### 枠を透明にして残す（`border: 1px solid transparent`）

B型で `border: 0` にすると **1px × 2 ぶん要素が縮み、祖先を通って環が 2px 上がる**（実測）。
場所だけ残して線を見せない。§6.1.5 のため。

#### iOS Safari の日付欄（`input[type=date]` / `datetime-local`）は箱を自力で決めない

**症状（本人報告・実機のみ）**: 親より横に広くなり、`SwipePager` の track 上で
**隣のページに重なって見える**。`width: 100%` / `minWidth: 0` / `boxSizing: border-box` を
全部与えても直らなかった。

**効いた対処（実機で確認済み・2026-08-04）**: `-webkit-appearance: none` + `appearance: none`
+ `maxWidth: 100%`。これで本人の端末で**横幅は直った**。タップでネイティブの日付ピッカーが
開く挙動はそのまま残る。

> **ただし「なぜ効いたか」は確定していない。** 有力な説は2つあり、どちらも一次情報で
> 裏が取れていない: (a) WebKit の UA スタイルが temporal input を `-webkit-inline-flex` で
> 描き、**その `display` のときに `width:100%` を無視する**（iOS 18 以降は修正済みという
> 情報もある）、(b) 内部UIの固有幅が `min-width: auto` として効く。**`appearance` は
> `display` を変えないので、(a) が真因なら効いた理由は別にある。**
> 断定して規範化しないこと（1周目に「実測: 親160pxで+16px溢れ」を根拠に規範化して外し、
> ここに至るまで3周かかった。BACKLOG F-39）。

**`appearance` を落としたら、縦も自分で決めること。** 幅と一緒に**縦方向の固有の寸法
（高さ・内部テキストの縦位置）も失われる**。実際、横幅を直した次の周に
「使用開始日だけ縦幅が変わった」と本人報告が来た。セットで必要なもの:

- `height` を**固定**する（`minHeight` は下限でしかなく、ネイティブ描画のままの `select` が
  それを上回ると、`appearance` を落とした欄だけが低くなって並びが揃わない）
- `lineHeight` を明示する（内部テキストが上寄せに落ちるのを防ぐ）
- `overflow: hidden`（内部UIがはみ出した場合の最後の歯止め）

> **Chrome では、この症状は横も縦も最初から再現しない。** Browser pane の実測は必ず
> 「揃っている」と出る。**この欄を触ったときの Chrome の実測は判定に使えない**ので、
> 必ず実機（iOS Safari）で確認すること。
>
> グリッド項目に置く場合は `minWidth: 0` も併せて付ける（グリッドの `min-width: auto` を
> 解くため。ただし**これ単独では iOS の問題は直らない**ことが実機で分かっている）。
> Chrome 実測の参考値: 最小内容幅 150px、親160pxで既定は +16px 溢れ、`minWidth: 0` で 0。
>
> **既知の未適用箇所**: 個別セッション詳細の `datetime-label`（`datetime-local`、幅を
> `190px` 固定で「理想値に設定」と同じ行に置いている）はこの作法をまだ適用していない。
> 本人からの報告が無く実機で確かめられないため意図的に触っていない（BACKLOG F-40）。

## 7. 「育てる」の作法

### 大前提（ここを取り違えない）

> **奏者が興味を持っているのは「今の自分の音」。**
> どれくらい練習したかの累計は、**サブ的に見れたら嬉しい**程度のもの。

したがって「育てる」は**主役を張らない**。画面の主役は常に今の音・今回の結果であり、
蓄積はその脇に、しかし確実に見える場所に置く。

DESIGN.md §1 の「蓄積が目に見えて育つこと」は、**蓄積を最大要素にせよという意味ではない**。
現状は蓄積が「見えない」ことが問題であって、「小さい」ことが問題なのではない。

### やること

- **主役は今の音・今回の結果**。累計はその脇に副次的に置く
- ただし累計は**確実に見える**こと（現在は累計指標がアプリ内に1つも存在しない）
- 空状態は「これから育つ」の語り口にする
  - 基準にする既存文言: **「録音するとここに折れ線が育ちます」**（`App.jsx:6556`）
- 蓄積を**形**で見せる（日ごとの縞、線が伸びる、記録が積み上がる）
- リードは消耗品。**開封後日数と使用量**が最も「育つ／老いる」対象

### やらないこと

- **累計を画面の主役にすること**（奏者が見たいのは今の音）
- バッジ・紙吹雪・レベルアップ演出
- **断定的な評価ラベル**（「平均より悪化」など）
- **開いた瞬間に赤で迎えること**
- 数値の自動フルスケール描画（±0.3¢のブレを画面いっぱいの起伏に見せない）

> DESIGN.md §1: 「観葉植物は静かに育つ」「和の間」。
> データタブを「反省する場所」から「見に行きたい場所」に変えるのが目的であって、
> 反省を強化するのが目的ではない。
